Every configured collection gets the same set of endpoints:

| Method | Path | Behavior | Success |
|---|---|---|---|
| `POST` | `/v1/{realm}/{database}/{collection}` | Create a document | `201` + `Location` + `ETag` |
| `GET` | `/v1/{realm}/{database}/{collection}` | List documents | `200` |
| `GET` | `/v1/{realm}/{database}/{collection}/{id}` | Fetch one document | `200` + `ETag` |
| `PUT` | `/v1/{realm}/{database}/{collection}/{id}` | Replace the whole document | `200` + `ETag` |
| `PATCH` | `/v1/{realm}/{database}/{collection}/{id}` | Partial update ([JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396)) | `200` + `ETag` |
| `DELETE` | `/v1/{realm}/{database}/{collection}/{id}` | Delete the document | `204` |
| `POST` | `/v1/{realm}/{database}/_batch` | [Create, replace, patch and delete atomically](#batch-writes) | `200` |

- An unknown realm, database, collection or `id` returns `404 not_found`. PUT and PATCH never create documents: there are no upserts, so create with POST and let the server choose the `id`.
- In a realm with `auth: enabled`, requests are decided by the collection's [access rules](../../auth/rules/), or allowed outright with an [API key](../../auth/api-keys/) in `Authorization: Bearer …`.
- Request bodies must be a single JSON object. Anything else returns `400 invalid_json`.

## Document shape

Documents are returned as bare JSON objects:

```json
{
  "id": "d2fjps30h2ipb32i2hg0",
  "_meta": {
    "created_at": "2026-09-25T21:30:00.000Z",
    "updated_at": "2026-09-25T21:45:12.345Z",
    "version": 3
  },
  "name": "Widget",
  "price": 12.5
}
```

- `id` is generated by the server ([xid](https://github.com/rs/xid): 20 characters, sortable by creation time). Clients can never choose it.
- `_meta` is owned by the server:
  - `created_at` is set on create and never changes.
  - `updated_at` is set on every write.
  - Both timestamps are RFC3339 in UTC with millisecond precision.
  - `version` is `1` on create and increases by one on every write.
  - In realms with `auth: enabled`, three ownership fields are added:
    - `owner` is the id of the signed-in user who created the document (or the user an API key [acted for](../../auth/api-keys/#acting-on-behalf-of-a-user)), or `null` when an [API key](../../auth/api-keys/) created it on its own. It never changes.
    - `created_by` is who created it, and never changes: `user:<id>`, `key:<name>`, or `anonymous` when a [create rule](../../auth/rules/) lets callers without credentials write.
    - `updated_by` is who made the last write, in the same form.

    Realms with `auth: disabled` don't have them. Documents stored before these fields existed don't gain `owner` or `created_by`; their next write adds `updated_by`.
- Single-document responses carry `ETag: "<version>"`, for example `ETag: "3"`.
- Documents written before versioning existed have no `version`. They get `version: 1` on their next write.
- `id`, `_id` and `_meta` in request bodies are always ignored.

## Create

```http
POST /v1/shop/orders/items
Content-Type: application/json

{ "name": "Widget", "price": 12.5, "status": "active" }
```

The body is validated against the collection's `schema.json`. The response is `201 Created` with the stored document and a `Location` header pointing at it.

## Validation errors

A document that fails its schema returns `400 validation_error` with one detail per failing field, using dot paths for nested fields:

```json
{
  "error": {
    "code": "validation_error",
    "message": "document failed schema validation",
    "details": [
      { "path": "address.city", "reason": "got number, want string" },
      { "path": "age", "reason": "minimum: got -1, want 0" },
      { "path": "extra", "reason": "is not allowed" },
      { "path": "name", "reason": "is required" }
    ],
    "request_id": "d2fk1a30h2ipb32i2hh0"
  }
}
```

## Concurrency and `If-Match`

Every write is conditional on the version it read, so concurrent writers never silently overwrite each other.

**`If-Match`**

- PUT, PATCH and DELETE accept an optional `If-Match` header with the version you expect, as returned in `ETag`:

  ```http
  PATCH /v1/shop/orders/items/d2fjps30h2ipb32i2hg0
  Content-Type: application/merge-patch+json
  If-Match: "3"

  { "price": 14 }
  ```

- If the document's current version differs, the response is `412 version_mismatch`, with the current version in `ETag`. This also happens when another write lands between the read and the write.
- `If-Match` can list several versions (`"3", "4"`) or be `*`, which means "any existing document".
- Weak tags (`W/"3"`) never match. Malformed values return `400 invalid_header`.

**Without `If-Match`**

- PUT and PATCH retry automatically when another write lands between their read and write: re-read, re-merge (PATCH), re-validate, write. They try up to 3 times, with a short random backoff.
- If every attempt loses the race, the response is `409 write_conflict`, and nothing from the request was applied. Clients may retry.
- A DELETE without `If-Match` deletes whatever version is current. When [access rules](../../auth/rules/) apply, the delete is conditional on the version the rule was checked against, and retries like PUT and PATCH: losing every attempt answers `409 write_conflict`.

{{< hint warning >}}
**A PUT without `If-Match` is last-write-wins.** It replaces whatever is stored, including changes made after you read the document, and nothing tells you. A PATCH that depends on a value you read has the same problem.

**Best practice:** send `If-Match` (the `ETag` you got) whenever a write depends on what you read: read-modify-write, counters, anything a user edited on a form. On `412`, re-read and decide. The [JavaScript client](../../clients/js/#concurrent-edits) has an `ifMatch` option.
{{< /hint >}}

## Unique conflicts

A create, replace or update that would repeat a value covered by a unique index (see [`indexes.json`](../../configuration/config-dir/#indexesjson)) returns `409 conflict`. The details name the index's fields:

```json
{
  "error": {
    "code": "conflict",
    "message": "a document with the same unique value already exists",
    "details": [ { "path": "email", "reason": "must be unique" } ],
    "request_id": "darf9mq5mh5g00aq9df0"
  }
}
```

For a compound unique index, each field is listed with the reason `must be unique in combination with a, b`.

## List

```http
GET /v1/shop/orders/items?limit=10&skip=20
```

```json
{ "items": [ ... ], "limit": 10, "skip": 20, "has_more": true }
```

By default documents are ordered by `id`, which is creation order. The endpoint also supports filtering (`where`), sorting (`order_by`) and counting (`count`). See [Querying](../querying/).

## Replace (PUT)

The body becomes the complete new document and is validated as a whole. Fields that aren't in the body are removed. `id` and `_meta.created_at` are kept.

## Update (PATCH)

The body is a [JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396) that is merged into the stored document:

- members in the patch overwrite stored values;
- nested objects are merged recursively;
- `null` removes a field.

The **merged** document is then validated against the schema.

```http
PATCH /v1/shop/orders/items/d2fjps30h2ipb32i2hg0
Content-Type: application/merge-patch+json

{ "price": 14, "discount": null }
```

{{< hint note >}}
Merge Patch can't set a field to a literal `null`: in a patch, `null` means "remove this field". To store `null`, replace the document with PUT.
{{< /hint >}}

## Delete

Deletes are permanent. The response is `204 No Content`, or `404` if the document doesn't exist.

## Batch writes

`POST /v1/{realm}/{database}/_batch` creates, replaces, patches and deletes documents across the database's collections in **one MongoDB transaction**: either every operation applies, or none does.

```http
POST /v1/shop/orders/_batch
Content-Type: application/json

{
  "operations": [
    { "op": "create", "collection": "orders", "document": { "item": "widget", "qty": 2 } },
    { "op": "patch", "collection": "stock", "id": "d2fjps30h2ipb32i2hg0", "patch": { "qty": 8 }, "if_match": "\"3\"" }
  ]
}
```

```json
{
  "results": [
    { "id": "o7", "item": "widget", "qty": 2, "_meta": { "version": 1, ... } },
    { "id": "d2fjps30h2ipb32i2hg0", "qty": 8, "_meta": { "version": 4, ... } }
  ]
}
```

- Each operation is `{ "op": "create" | "replace" | "patch" | "delete", "collection": "...", ... }`. `create` and `replace` need `document`; `patch` needs `patch` (a JSON Merge Patch, same rules as [PATCH](#update-patch)); `replace`, `patch` and `delete` need `id`. Any of them accepts `if_match`, exactly like the `If-Match` header (a version such as `"3"`, or `"*"` for any existing document).
- `results` has one entry per operation, in the same order: the written document for `create`, `replace` and `patch`; just `{ "id": ... }` for `delete`.
- Up to 100 operations per batch.
- Each operation is validated against its collection's `schema.json` and, in realms with `auth: enabled`, checked against the collection's `create`/`update`/`delete` [access rule](../../auth/rules/) — exactly like a single write. API keys bypass rules, as they always do.
- The **first** operation that fails aborts the whole batch: nothing from any operation is applied. The response is the usual error envelope, with the failing operation's position (`0`-based) as the `path` in `details`:

  ```json
  {
    "error": {
      "code": "version_mismatch",
      "message": "operation 1: If-Match does not match the current version \"4\"",
      "details": [ { "path": "1", "reason": "If-Match does not match the current version \"4\"" } ],
      "request_id": "darf9mq5mh5g00aq9df0"
    }
  }
  ```

  A schema validation failure inside an operation prefixes the field path too, e.g. `"1.qty"`.
- On a version mismatch a batch answers `412`; see the note below.
- The [JS client](../../clients/js/): `client.db('orders').batch([{ op: 'create', collection: 'orders', document: {...} }, { op: 'patch', collection: 'stock', id, patch: {...}, ifMatch }])`.

{{< hint note >}}
Unlike PUT and PATCH, a batch **never retries a version mismatch itself**: read, batch with `if_match`, and on `412` re-read and build the batch again. For the order-and-stock example above, re-read the stock document's current version and quantity, then send a new batch with the decremented amount.
{{< /hint >}}

## Schema changes

After `schema.json` changes, existing documents are returned as they are, even if they no longer match. Every write must produce a document that is valid against the **current** schema.

{{< hint note >}}
Changing a schema never rewrites stored documents, so an old document that no longer matches can still be read but cannot be saved again until it is fixed. After a breaking schema change, migrate the data before relying on writes to it.
{{< /hint >}}
