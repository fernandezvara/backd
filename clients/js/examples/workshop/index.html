1 A function that reads as the caller order_total

The tax rule belongs on the server, not in every client. The function reads the order as the caller, so the collection's rules still decide who may see it.

Sign in as Ada or Bob to place orders.

No orders yet.

What to notice
  • The customer can create drafts and nothing else: the collection's rules forbid setting any other status.
  • Ask for an order as the other customer: 404 not_found, exactly as if it didn't exist. The function runs with the caller's own access.
The code
const db = backd.db('main')
await db.collection('orders').create({ item, quantity, amount, status: 'draft' })
const { subtotal, tax, total } = await db.fn('order_total', { order_id })

2 A privileged, idempotent refund refund

Marking an order refunded is something no customer rule may allow, so it is a function with admin access, for staff only. A retried request must not refund twice.

Sign in as Staff (or as a customer, to see the refusal).

Orders you place as Ada or Bob in step 1 appear here. Staff can't list customers' orders; the refund asks for an order id.

The refund queued a receipt: job is ·

What to notice
  • As a customer the call is refused (403): the function's invoke rule lets only staff in.
  • The same key again returns the same refund. A new key means "another refund", and the order is already refunded: 409 not_refundable. "Two at once" shows one run and a replay.
  • The order change and the refund record are one transaction. The receipt is written by an internal function (refund_receipt) that has no HTTP route: refund queued it with ctx.call.
The code
const out = await db.fn('refund', { order_id, reason }, { idempotencyKey: `refund-${order_id}` })
// out.receipt_job: the job refund queued for refund_receipt

3 A webhook from a payment provider payment_webhook

Another service calls this URL. It has no backd session, so the function is the only check: it verifies the signature, ignores events it already handled, and marks the order paid.

This page plays the provider. It signs the exact body with the shared secret (HMAC-SHA256) and sends it, with no credentials.

The function reads its shared secret from backd's encrypted secrets.

What to notice
  • A wrong signature: 400 invalid signature. The function checks it against the raw body, byte for byte.
  • The same event twice: already processed. A unique index on the event id makes a retry harmless.
  • With the secret unset the function answers secret_missing until an operator sets it.
  • Customers can't mark orders paid; this function can, because it declares admin: true. After a signed event, switch to the customer: the order is paid.
The code
const body = JSON.stringify({ id: 'evt_1', type: 'payment.succeeded', order_id })
await fetch(`${origin}/v1/workshop/main/_func/payment_webhook`, {
  method: 'POST',
  headers: { 'x-signature': await signBody('whsec_test', body) },  // sha256=<hmac of body>
  body,
})

4 A report in the background export_orders

Work that may take a while, or must survive the caller leaving, is an async function: the call answers at once with a job, and a worker runs it.

Sign in as Ada or Bob: the report holds that customer's orders.

What to notice
  • The call answers 202 with a job and a Location. The page polls it: queued → running → done.
  • The function runs as the customer (ctx.db), so the report holds only their orders and only they can read it.
  • A job runs at least once. The function keys its report on the request id, so a second run returns the report it already wrote.
  • Rate limited: 5 exports per customer per hour.
The code
const job = await db.fn('export_orders', {})   // a Job handle: 202 + Location
while ((await job.status()) !== 'done') await sleep(500)
const { report_id, rows } = await job.wait()   // the function's output
const report = await db.collection('reports').get(report_id)

What to notice
  • nightly_cleanup and daily_digest run by themselves (03:00 and 00:00 UTC) on a worker. A run by hand goes through the admin API; nightly_cleanup is internal, so it has no HTTP route at all and this is the only way in.
  • Tries above 1 means a worker was lost or the function is being retried; Next attempt says when a failed attempt will run again (a function's retry).
  • Pick the call of a refund in the history: its tree shows refund_receipt under it, with origin function. That is ctx.call, followed through parent_id.
  • Secrets show who set them and when, never their values.
The code
await backd.admin.secrets.list()                    // metadata only
await backd.admin.jobs.list({ scheduled: true })     // cron runs, with attempts and next_attempt_at
await backd.admin.invocations.list({ requestId })    // every call of one request, with parent_id
const job = await backd.admin.invokeFunction('main/nightly_cleanup')   // run by hand
await job.wait()

6 Email email-capture

backd never sends mail itself: the realm names a delivery function that hands each message to your provider. In this realm that function only stores the messages, so you can read them.

Open the Mailbox to read what the realm "sent".

What to notice
  • The message and its link are made by a worker at send time; backd stores only a hash of the token, never the message.
  • Emails appear in the Mailbox once account flows send them (verification and password reset are on the roadmap); the delivery path itself is already tested end to end.
