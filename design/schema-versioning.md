# Design: schema versioning and migrations

- **Issues:** milestone `43-schema-versioning`, #943 (this design) and #944–#953 (§16).
- **Status:** decided (2026-11-14). The shape was settled over several rounds of review (§17), and the points this document added were accepted with it (§18).
- **Builds on:** the functions runtime ([decisions: Deno, one process per call, `backd-server functions build`](../docs/content/docs/build/functions/_index.md)), the job queue, and `encrypt migrate` ([field-encryption.md](./field-encryption.md)), whose background job this one copies.
- **Related designs:** [types-openapi.md](./types-openapi.md) (generated types, `realm.json`, `X-Backd-Types`), [export-import.md](./export-import.md), [triggers-and-realtime.md](./triggers-and-realtime.md), [custom-ids.md](./custom-ids.md) (another "existing documents keep their form" change).

## 1. The problem

A collection's `schema.json` is enforced when a document is written. Changing it never touches stored documents:

- An old document can be read but **not saved again** until someone fixes it ([`documents.md`, "Schema changes"](../docs/content/docs/build/api/documents.md)).
- `backd data check` finds documents that no longer match, but nothing records **which schema a document was written under**, and nothing fixes them.
- Apps, rules, triggers and functions can't tell an old document from a new one except by guessing from its fields.
- Mobile apps make it harder. Old versions of an app stay installed for months and keep reading and writing the old shape, and nobody can force them to update.

Schema versioning gives every document a version, lets the developer write the migration from one version to the next, and has backd apply it in the background. **No request ever waits for it.** Old apps keep working when the change is made compatible, and are told to update when it can't be.

**What this is not:** a database migration tool for backd's own system collections (those change in releases, with `backd-server provision`); a way to change a collection's custom ids, organization or files; or down-conversion of new documents for old apps (§17, rejected).

## 2. Decisions at a glance

| Topic | Decision |
|---|---|
| Files | `schema.vN.json` per version and `schema.vN.ts`, the migration from N−1 to N, both **in the collection folder**; `schema.d.ts` generated next to them. No other folders, no version key: the highest N is current (§3). |
| Unversioned | A plain `schema.json` is a collection without versions, counted as v1. A document without `_meta.schema_version` is **always v1**. |
| Memory | The server compiles **only the current schema**. Old schema files are read only by `backd types`; keeping them is the developer's choice (§4). |
| Migrations | TypeScript only, typed `(doc: V1, meta: Meta) => V2`, pure and synchronous, one step each (§5). |
| Type-checking | Migrations are always bundled with `--check` by `backd-server functions build`, and in dev at start and on watch. Startup refuses missing or stale bundles (§6). |
| Where they run | **Only in the Deno executor, in batches, in a background job.** Never in a request, never on a read. **No embedded JavaScript engine**, rejected since the start of backd (§8, §17). |
| When | At **every start**, for every versioned collection: an indexed count, then a job if anything is below the current version. No `migrate_on_start`; startup is never delayed (§8). |
| A migration write | Bumps `_meta.version`, keeps `updated_at` and `updated_by`, isn't seen by triggers or realtime. A failure leaves the document at its version and is reported (§8.5). |
| Reads | Return documents **as stored**, so lists can mix versions while a migration runs. Typed as a union keyed by `_meta.schema_version` (§9.1, §11). |
| Writes | Validated against the current schema; **no 409** for old documents. Stamped with the version the app **declares** in `X-Backd-Schema-Version` (per collection, sent by the clients), or the current one when none is declared (§9.2). |
| Old apps | Expand, then contract; a compatibility check at build time; `min_schema_version` answering `426 upgrade_required` (§10). |
| TypeScript apps | Get a generated `upgrade()` from the migration files, the same code the server runs. Dart, Go and Python apps convert by hand with the generated types (§11). |

## 3. Files

```
main/assets/
  collection.yaml      may set min_schema_version (§10.3)
  indexes.json
  rules.yaml
  schema.v1.json
  schema.v2.json
  schema.v2.ts         migration v1 → v2
  schema.v3.json       the current version: the highest number
  schema.v3.ts         migration v2 → v3
  schema.d.ts          generated by backd types (§11.1)
```

Rules the registry enforces when it loads a collection (each is a startup error that names the file):

- Names: `schema.v<N>.json` and `schema.v<N>.ts`, N a positive integer without leading zeros. Anything else that starts with `schema.` (other than `schema.d.ts` and `schema.json`) is an error, so a typo such as `schema.V2.json` doesn't go unnoticed.
- `schema.json` together with any `schema.vN.json` is an error ("rename `schema.json` to `schema.v1.json`").
- Every `schema.vN.ts` needs its `schema.vN.json`. A `.ts` without its JSON is an error.
- Versions may have gaps at the bottom (old ones deleted), but **the chain from the lowest kept JSON to the current one must be continuous in `.ts` files**: for every kept `schema.vN.json` above the lowest, `schema.vN.ts` exists. The lowest kept version needs no `.ts`. A missing step is a *warning* when documents may still need it (§4).
- `schema.v1.ts` is an error: there is no version 0.
- `schema.d.ts` is generated and never read by the server.
- Only the current `schema.vN.json` goes through the existing checks of `schema.json` (draft 2020-12, the allowed keywords, `x-backd-*`, references, encrypted and file fields).

**Adopting versions.** Rename `schema.json` to `schema.v1.json` and change nothing else: the collection is versioned at v1, its documents are v1 (missing stamp), nothing is migrated. Add v2 when the first change comes.

## 4. What the server holds, and what it does with old files

- **Memory:** the compiled current schema, as today, plus the collection's current version number and `min_schema_version`. No old schema is compiled or kept.
- **Old JSON files** are for `backd types` (the per-version types and the compatibility check, §6.2) and for history. The developer keeps or deletes them.
- **Migrations** are bundles on disk, listed in the build manifest, sent to the executor by the job (§8). They are not loaded into `backd-server`.
- **Deleting old versions.** Delete `schema.v1.json` and `schema.v2.ts` together; v2 becomes the lowest kept version. If stored documents are still at v1, the job can't move them up:
  - the start-up count reports them, and so do `data check` and a warning in the startup log: `main/assets: 12 documents at version 1 have no migration to version 2`;
  - they stay readable;
  - a write to one succeeds only if the result is valid against the current schema, as today.

  Startup does not refuse: it's the developer's decision.

## 5. The migration file

### 5.1 Contract

```ts
import type { V1, V2, Meta } from "./schema.d.ts";

export default function (doc: V1, meta: Meta): V2 {
  /* return the document in version 2 */
}
```

1. **One default export**, a function of `(doc, meta)` that returns the next version's fields. The only import allowed is `import type` from `./schema.d.ts`; the build refuses anything else (a value import would need a runtime and could pull code from anywhere). Helper functions in the same file are fine.
2. **`doc` holds the fields only**, as they are stored and as the reader with full rights sees them: no `id`, no `_meta`. Encrypted fields are plain (§8.4). Anything the function returns under `id` or `_meta` is ignored.
3. **`meta` is read-only**: `id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `owner`, and `org` and `team` when the collection uses them, and `version` (the write version, not the schema version). It lets a migration decide from who owns a document or when it was made, without a database call.
4. **Pure and synchronous.** No `await`, no promise, no `ctx`, no I/O. The same input must give the same output, because the job may run a document more than once (a retry, a concurrent edit, a v1 write after the migration). The runner enforces it (§5.2).
5. **One step.** `schema.v3.ts` receives a v2 document. The job chains the steps: a v1 document goes through `schema.v2.ts`, then `schema.v3.ts`, in one executor call.
6. **Only the final result is validated**, against the current schema, which is the only one in memory. An intermediate result is not checked against its version's JSON; the types (§11.1) are what keep each step honest.
7. **What a migration may not change** (the document fails if it does, §8.5): file fields (`x-backd-file`), whose objects and accounting belong to the file machinery; and anything that backd owns (`id`, `_meta`, the organization and the team, which live in `_meta`).

### 5.2 Determinism, enforced

The executor runs migrations in a **`migrate` mode** of `runner.js`, with no permissions except reading the bundle (no `--allow-net`, no environment, as for functions). Before the bundle loads, the runner makes the clock and randomness unavailable:

- `Date.now()`, `new Date()` without an argument, `performance.now()`, `Math.random()`, `crypto.getRandomValues()` and `crypto.randomUUID()` **throw**.
- `new Date(value)` and `Date.parse` still work, because converting stored dates is legitimate.
- A function that returns a promise fails the document ("a migration must be synchronous").

The result must survive a JSON round trip (no `undefined` at the top level, no functions, no `NaN`). Dates come in and go out as the strings the API uses; `x-backd-store: date` fields are converted on the way to MongoDB by the normal write path.

### 5.3 Example

The full three-version example is in §13; this is its first step:

```ts
// main/assets, v1 → v2 (expand): description duplicates body, so v1 apps keep reading
// body; every asset gets a visibility.
import type { V1, V2, Meta } from "./schema.d.ts";

export default function (doc: V1, meta: Meta): V2 {
  return {
    ...doc,
    description: doc.body ?? "",
    visibility: doc.published_at ? "public" : meta.org ? "team" : "public",
  };
}
```

## 6. Building and checking

### 6.1 The build

`backd-server functions build` (and the dev server at start and on every change) also builds migrations:

- **One bundle per collection** holding all its steps, `deno bundle --check` always, whatever the `--check` flag says for functions. Migrations are small, and a type error in one corrupts data rather than failing a call.
- Bundles go to `<database>/_migrations/.build/` with their own `manifest.json` (content hashes, the Deno version), next to the functions' `.build/` and gitignored the same way. A database without functions gets the folder anyway. It's a build output, not a folder the developer writes in, so the "no other folders" decision holds for sources.
- **Startup refuses** a versioned collection whose bundle is missing or stale (the sources' hash differs), exactly as it does for functions. Since migrations are only ever bundled with `--check`, a production start can't run a migration that didn't type-check. That closes the "type errors at a production start" question.
- Dev mode rebuilds on change and logs the type errors. The collection keeps its last good bundle until the error is fixed.

### 6.2 The compatibility check (part B of §10)

The same build compares each kept `schema.vN.json` with the one below it, statically, and **warns** (it never fails the build) when:

| Finding | Example | Why it matters |
|---|---|---|
| **v(N) refuses a write v(N−1) allowed** | a new field in `required`; a narrower `type`, `enum`, `maxLength`, `pattern`; `additionalProperties: false` newly set | apps on v(N−1) get `400` |
| **v(N) drops a field v(N−1) declared** | `body` removed | apps on v(N−1) read documents without it |
| **v(N) changes a field's type** | `tags` from string to array | both of the above |

Each warning names the version, the path and the rule. It also says whether `min_schema_version` already excludes the affected apps, in which case the warning becomes a note. It's a sound subset of JSON Schema comparison, not a full one: `oneOf`, `if/then`, `$ref` changes and conditional keywords are reported as "can't tell, check by hand" rather than guessed.

## 7. Stored documents

- **`_meta.schema_version`**: an integer, server-owned like `_meta.version`. Missing means 1. Clients can't write it, rules can read it.
- It is **set on every write** (§9.2) and by the job (§8).
- **Index:** provisioning creates `{ "_meta.schema_version": 1 }` on every versioned collection with more than one version file. It's created idempotently and never dropped, as the provisioning decision says for every index; backd already creates indexes of its own (soft delete, TTL). The count and the job query `{"_meta.schema_version": {"$in": [null, 1, …, N−1]}}`, which uses the index and matches missing stamps through `null`.
- **The MongoDB validator** stays the current schema at `validationLevel: moderate`. Writes of any version are validated against the current schema in backd and in MongoDB. Documents at old versions that no longer match are left alone by MongoDB, as today.

## 8. The migration job

### 8.1 Starting it

At every start, each instance with the **worker** role does this for each versioned collection whose current version is above 1:

1. Count the documents below the current version (§7). Zero ends it, in milliseconds.
2. Otherwise queue a job `schema-migrate:<realm>/<database>/<collection>@<current>`. The id makes it idempotent, so many workers starting together queue it once. A job for an earlier target that is still running is cancelled, and the new one picks up from the start of the collection: a v3 job also migrates the documents a v2 job hadn't reached.

There is no setting to block startup until the job ends (§17): with one instance it would be an outage, and in a rolling deploy it wouldn't stop old instances from writing old versions. There is also no setting to turn the automatic start off. The files are the reviewed intent, and `backd data migrate --dry-run` (§8.6) answers "what would happen".

### 8.2 Running it

The job reuses `encrypt migrate`'s machinery (`internal/httpapi/worker_encrypt.go`, `internal/auth/encryptjob.go`):

- It reads the collection **in id order**, filtered to versions below the current one, and stores its position after every batch. If a worker dies, another resumes from there.
- **Batches** of up to 500 documents or 4 MiB go to the executor in one `migrate` call: `{bundle, current, docs: [{id, version, schema_version, meta, fields}]}`. Each document gets back `{id, fields}` or `{id, error}`.
- **Rate:** at most 1,000 documents a second per job, as `encrypt migrate`, so requests using the collection aren't starved. There's no setting until someone needs one.
- **Executor capacity:** migration calls use their own small concurrency limit (one per job, at most two per realm), so a backfill can't take `EXECUTOR_MAX_PROCESSES` away from functions.
- A call that times out is retried once with the batch split into single documents. The document that still times out is reported (§8.5). Nothing else in the batch is lost.

### 8.3 Writing the result

For each migrated document, the job validates the result against the current schema, then writes it **conditionally** on the `_meta.version` it read:

- **On success:** the fields are replaced, `_meta.schema_version` becomes the current version, and **`_meta.version` is bumped**, because the content changed. A client holding the old ETag gets `412` on its next conditional write and reads the document again, instead of patching the old shape.
- **`updated_at` and `updated_by` don't change.** It isn't a person's edit, and "last edited" in apps stays truthful.
- **If the version moved** (someone wrote meanwhile), the job reads the document again once. If it is now at the current version, it's skipped. If it's still old (an old app wrote it, §9.2), it's migrated from its new content.
- **Unique indexes** apply as on any write. A duplicate is a failure of that document (§8.5).
- **Triggers and realtime are not told**, as for `encrypt migrate`; a million documents must not mean a million trigger runs. The next read or event of the document carries its new version and content. This is documented: a realtime subscriber may hold a document in the old shape until it changes again or the page reloads.
- Searchable encrypted fields get their blind indexes recomputed by the normal write path.

### 8.4 Encrypted fields

The job reads documents with full rights, decrypting as an administrator reading through the admin data route does. Migrations therefore see plain values, as functions do through `ctx.db`. The result is encrypted again on write. This is the same exposure functions already have (plain values in the executor's memory, never logged). The docs page on field encryption gets one line about it.

### 8.5 Failures

A document fails when its migration throws, times out, returns something that isn't JSON or isn't valid against the current schema, changes a file field, or breaks a unique index. A failed document:

- **stays at its version**, untouched;
- is recorded in the job's report with its id, the step (`2 → 3`), the reason and, for a validation error, the path and the schema keyword. **Never a value.** At most 1,000 failures are kept per job, then only a count;
- is tried again at the next start, because it is still below the current version;
- is counted in `backd_schema_migration_documents_total{result="failed"}`.

The job ends `complete` (all migrated), `partial` (some failed) or `cancelled`. A failure never stops the job.

### 8.6 Commands and the admin API

- `backd data migrate --realm R --database D --collection C [--wait] [--dry-run] [--json]`:
  - with `--wait` it follows the running job, or starts it, and exits `0` when complete and `1` when partial;
  - with `--dry-run` it runs the migrations, validates the results and writes nothing, reporting what would fail;
  - it needs a full administrator, like `data check`.
- `backd data migrations --realm R [--database D --collection C]` lists the latest report per collection.
- The admin API gets `POST /_admin/data/migrate` and `GET /_admin/data/migrations`, mirroring `data check`'s routes; see OpenAPI.
- **Audit:** `data.migrate` when a job is started by hand (`collections`, `dry_run`, `job_id`), and `data.migrated` when any job ends (`collection`, `from`, `to`, `migrated`, `failed`, `complete`; never values). Both get rows on the audit page; `scripts/check-docs-audit.py` makes sure of it.
- **Metrics:** `backd_schema_migration_documents_total{realm,collection,result}` and `backd_schema_documents_below_current{realm,collection}`, which is set by the start-up count and the job.

### 8.7 When there is no executor

A realm with a versioned collection but no executor configured (`BACKD_EXECUTOR_URL` unset) still starts. The start-up count logs a warning when documents are below the current version ("12 documents won't be migrated: no executor"), the gauge shows them, and requests are unaffected. If the executor is down, the job waits and retries like any job. The alternative, refusing to start, would force an executor on realms that keep old migrations only for history.

## 9. Requests

### 9.1 Reads

**A read returns every document as stored**, with its `_meta.schema_version`. While a job runs, a list can mix versions. This is the price of not having a maintenance window and of not running code on reads. It's documented as the first thing to know about versions, with what an app does about it (§11).

- **Expanded references** come back at their own version.
- **Realtime events** carry the document as stored, with its version.
- **Triggers** receive `before` and `after` as stored.
- **Functions** reading through `ctx.db` get stored documents. Their generated types are the same union (§11.1).
- `where` and `order_by` accept `_meta.schema_version`, so an app or a script can find what is still old.

### 9.2 Writes

**Every create, PUT, PATCH and `_batch` operation is validated against the current schema.** There's no 409 for old documents:

- An app that holds an old document converts it (§11.2) and sends the whole new shape with **PUT** and `If-Match`.
- A PATCH on an old document is merged into the document as stored, and the result must be valid against the current schema. When it isn't, the answer is `400`, as today.
- Triggers, realtime and rules see these writes as they see any write.

**The version stamp is the version the app declares.** Generated clients send:

```
X-Backd-Schema-Version: main/assets=1, main/pins=3
```

- The version stamped is the declared one for the collection written, or **the current version when none is declared** (untyped clients, scripts, functions, server code).
- **Why:** a v1 app editing a v2 document changes only `body`. Stored as v1, the document is migrated again by the next start's job, and every v2 app reading it runs `upgrade()` first (§11.2), so `description` is copied from the new `body` and the duplicated data stays honest (§13).
- No old schema is needed for this, because the write is still validated against the current one. That is why changes must be compatible for the versions apps still use (§10).
- **A declared version above the current one** is `400 schema_version_unknown` ("deploy the server before the apps").
- **A declared version below `min_schema_version`** is `426 upgrade_required` (§10.3).
- **Parsing:**
  - entries for collections the request doesn't touch are ignored;
  - a malformed header is `400 invalid_schema_version`;
  - a collection without versions ignores its entry.
- **Which entries the clients send:** the collection of the path, the collections of `expand`, and each collection of a `_batch`.
- **CORS:** the header joins the allowed request headers. It is not a credential.
- **Functions' `ctx.db` writes** send no header and stamp the current version. A function that writes on behalf of an old app's data must produce the current shape.

## 10. Apps you can't force to update

The docs say this plainly: **this is the only way to keep apps working whose updates are outside your control.** It takes more than one release, and for a while data is duplicated. It also says why the goal is to move every client to the current version as soon as possible: each version still in use is one more branch in every app's `switch`.

### 10.1 A: expand, then contract

A breaking change is split in two:

1. **Expand:** the new version adds the new fields next to the old ones, all optional, so writes from the previous version stay valid. Its migration fills the new fields from the old ones. Apps of the new version write both.
2. **Contract:** a later version removes the old fields from the schema without forbidding them (no `additionalProperties: false` for them). Apps one version behind may still send them; stamped with their version, the job and `upgrade()` clean them. Its migration drops them, and `min_schema_version` is raised to exclude the apps that only read the old fields.

### 10.2 B: the compatibility check

§6.2: the build warns about each step that breaks the version below it, so the developer knows before deploying which apps a change affects.

### 10.3 C: `min_schema_version`

```yaml
# collection.yaml
min_schema_version: 2
```

- A request that declares a version **below it for that collection** (list, get, any write, `_batch`, `expand`, a realtime subscription) answers **`426 upgrade_required`** with `{"collection": "main/assets", "min": 2, "declared": 1}`. Reads are refused too, because an old app would misread the new shape. An app shows "please update" from this one error.
- **Requests that declare nothing are never refused**: server code, scripts and untyped clients aren't apps in the field.
- Not a security control: an app can declare anything. It's a compatibility signal.
- It must be between 1 and the current version; the registry refuses anything else.

## 11. Clients and types

### 11.1 Generated types

- **`schema.d.ts` per versioned collection**, written by `backd types` and by the dev server on change. It's checked for drift by `backd types --check`. It holds `V1…VN` (the fields of each kept version, from its JSON file), `Meta`, and `Current`. Migrations import from it, so a collection in a database without functions still has its types.
- **The realm's generated types** (TypeScript, Dart, Go, Python, and `backd.d.ts` for functions):
  - `MainAssets` becomes the union of the kept versions, **discriminated by `_meta.schema_version`**: a TypeScript union, a Dart sealed class with one subclass per version, and in Go and Python one type per version with a decoder that picks by the version;
  - write inputs are the current version only;
  - once only one version is kept, the union collapses to one type, and code that handled old versions gets a compiler error where a `case` no longer exists.
- **`realm.json`** gets `schema_versions: {"main/assets": 3, …}`, which the clients send as the header (§9.2).
- **The per-realm OpenAPI** documents `_meta.schema_version`, the header, `426` and `schema_version_unknown`.

### 11.2 Converting in the app

```ts
import { upgrade, type MainAssets, type MainAssetsV3 } from "./backd";

function current(asset: MainAssets): MainAssetsV3 {
  switch (asset._meta.schema_version) {
    case 1:
    case 2:
      return upgrade.mainAssets(asset);   // the server's own migrations: v1 → v2 → v3
    case 3:
      return asset;
  }
}

const edited = { ...current(asset), title: "New title" };
await assets.replace(asset.id, edited, { ifMatch: asset._meta.version });
```

- **TypeScript and JavaScript** get `upgrade` from `backd types --lang ts`, which writes a runtime module next to the types (`migrations.ts`), bundled from the migration files. It is the same code the server runs, so app and server can't disagree. `meta` comes from the document's `_meta`. The determinism rules (§5.2) hold there too: the module wraps the call the same way.
- **Dart, Go and Python** get the per-version types and write the conversion by hand, the same `switch`. The docs show it in each language.
- **All four clients** send `X-Backd-Schema-Version` from the generated `schema_versions` when they're created with the generated realm (the typed accessors). The JavaScript, Dart and Python clients already take `types` for the stale-types warning; the versions travel the same way. Untyped use sends nothing.
- `426 upgrade_required` is its own error class in each client (`UpgradeRequiredError`), never retried.

## 12. Everything else that sees the version

| Area | What changes |
|---|---|
| **Rules** | `document._meta.schema_version` is readable, like the rest of `_meta`, so a rule can treat versions differently during a transition. `data` (the incoming write) is the current shape. |
| **Export and import** | Packages record each collection's current version and every document's `_meta.schema_version`. Import stamps documents with the version they carry. An import into a newer version leaves them below current, and the next start's job migrates them. Import validates against the target's current schema as today, so an incompatible old document is `invalid` in the report. |
| **`data check`** | Reports counts per version and checks each document against the current schema, as today. A document below current that doesn't match isn't drift: it's "waiting for migration" and is counted apart. |
| **Admin UI** | Shows a document's version, a collection's counts per version and the latest migration report. "Migrate now" starts the job. The data editor writes the current shape. |
| **Change feed** | Unchanged: events carry stored documents. |
| **Soft delete** | Documents in the trash are migrated too, so a restore brings back a current document. |
| **Custom ids, organizations, teams** | Untouched by migrations (§5.1). |

## 13. Example: Shelf's `main/assets` in three versions

`body` becomes `description`, and every asset gets a `visibility`, without breaking the apps already installed:

| Version | The document holds | Apps that work | Migration |
|---|---|---|---|
| **v1** | `body` | v1 | — |
| **v2** (expand) | `body` and `description` (the same text); `visibility` optional | v1, v2 | `schema.v2.ts`: copies `body` to `description`, sets `visibility` |
| **v3** (contract) | `description`, `visibility`; `body` is no longer declared | v2, v3; `min_schema_version: 2` turns v1 apps away (`426`), because they read `body` | `schema.v3.ts`: drops `body`, fills a missing `visibility` |

`schema.v1.json` (Shelf's current `schema.json`, trimmed):

```json
{
  "type": "object",
  "properties": {
    "title": { "type": "string", "minLength": 1, "maxLength": 200 },
    "kind": { "enum": ["link", "note", "file"] },
    "url": { "type": "string", "format": "uri" },
    "body": { "type": "string" },
    "tags": { "type": "array", "items": { "type": "string", "minLength": 1, "maxLength": 40 }, "maxItems": 12 },
    "published_at": { "type": ["string", "null"], "format": "date-time", "x-backd-store": "date" },
    "downloads": { "type": "integer", "minimum": 0 }
  },
  "required": ["title", "kind"]
}
```

`schema.v2.json`: v1 plus two optional fields, so every v1 write stays valid and the compatibility check is silent:

```json
    "body": { "type": "string" },
    "description": { "type": "string" },
    "visibility": { "enum": ["team", "public"] },
```

`schema.v2.ts`: in §5.3.

`schema.v3.json`: `body` is no longer declared (and not forbidden, so v2 apps that still send it aren't refused). The check notes "v1 readers lose `body`", and `min_schema_version: 2` acknowledges it:

```json
    "description": { "type": "string" },
    "visibility": { "enum": ["team", "public"] },
```

`schema.v3.ts`:

```ts
// main/assets, v2 → v3 (contract): body goes; description is the only text.
import type { V2, V3 } from "./schema.d.ts";

export default function (doc: V2): V3 {
  const { body, ...rest } = doc;
  return { ...rest, description: doc.description ?? body ?? "", visibility: doc.visibility ?? "team" };
}
```

What happens to one asset over time:

1. **v3 is deployed.** At start, the job finds 40,000 assets below v3 and migrates them in about 40 seconds, while every request is served. Lists mix v2 and v3 until then. v3 apps run `upgrade()` on the v2 ones.
2. **A v2 app**, not yet updated, edits an asset and sends `body` and `description`. The write is valid against v3 (`body` isn't forbidden) and is stamped **v2**. v3 apps reading it upgrade it in memory, which drops `body`. The next start's job stores it as v3.
3. **A v1 app** asks for the list and gets `426 upgrade_required`. It shows "please update".
4. **Later**, `visibility` can become required in a v4, with `min_schema_version: 3`, once no v2 app is left. The check warns about it until then.

## 15. Security considerations

- **Migrations are code from the configuration**, reviewed in git like rules and functions. They run in the executor's sandbox with fewer rights than a function: no network, no `ctx`, no secrets, no clock, no randomness.
- **The executor sees plain documents** during a migration, as it does for functions that read data (§8.4). Nothing from a migration is logged except the function's own `console` output, which goes through the executor's masking like a function's.
- **Reports never hold values:** ids, paths, schema keywords, reasons.
- **The header is not trusted for anything but compatibility.**
  - Declaring an old version makes a write stamped old, so the document is migrated again: harmless, idempotent by §5.1.
  - Declaring a version below `min_schema_version` only refuses the caller's own request.
  - Validation is always against the current schema, so the header can't get invalid data stored.
- **Availability:** no request waits for a migration, and a migration can't take the executor's capacity from functions (§8.2).

## 17. Decisions taken (2026-11-13/14)

| Question | Answer |
|---|---|
| Version per realm or per collection? | Per collection. |
| Where the files live | `schema.vN.json` and `schema.vN.ts` in the collection folder, so the layout is predictable; no `schemas/` or `migrations/` folders, no version key. |
| Migration language | TypeScript only (no declarative YAML), typed, with a `meta` argument. |
| Old-version types | A generated `schema.d.ts` per collection. |
| A failed migration | Leaves the document at its version. |
| Type-checking | At `functions build --check` when preparing a production deploy, and at dev startup and on watch. |
| Where migrations run | The Deno executor, in background jobs. An embedded JavaScript engine was rejected since the start of backd. |
| Upgrade on read | Rejected: no function call on reads, so end users never pay for a migration. |
| `migrate_on_start` | Rejected: the job always runs in the background at every start, and most collections finish in milliseconds. |
| 409 for old documents | Dropped entirely: writes are validated against the current schema, and apps convert and PUT. |
| Mixed versions in reads | Accepted and documented as the price of no maintenance window. |
| Migration writes | Bump `_meta.version`, keep `updated_at` and `updated_by`, don't reach triggers or realtime. |
| Documents without a version | Always v1. |
| Old schema files | The developer's responsibility; the server keeps only the current schema in memory. |
| `upgrade()` | Generated for TypeScript from the migrations; other languages convert by hand. |
| Old apps | Expand and contract, the compatibility check, `min_schema_version` with `426`, documented as the only way to support updates outside your control, with the data duplication it implies. |
| The write stamp | The version the app declares, per collection. |
