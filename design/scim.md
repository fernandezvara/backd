# Design: SCIM provisioning (organizations and realm)

- **Issues:** not created yet (milestone to be named after the design is agreed)
- **Status:** draft; the decisions of §13.1 are agreed, §13.2 lists what is still open
- **Related designs:** [sso.md](./sso.md) (providers, connections, joining, `blocked`, and §10 verified domains: proof of domain ownership, discovery, linking), [scoped-sessions.md](./scoped-sessions.md) (§4.5 ending access, §6 `sso_required`), [organizations.md](./organizations.md) (members, roles, capabilities, hooks), [account-lifecycle.md](./account-lifecycle.md) (erasure, disabling), [breach-response.md](./breach-response.md) (session revocation)

## 1. The idea

An identity provider (Microsoft Entra ID, Okta, JumpCloud, OneLogin, and Google Workspace where its admin console allows it) keeps the list of people of a company. SCIM 2.0 (RFC 7643/7644) is the protocol it uses to **push** that list to an application: create, update, deactivate and delete users, and the groups they belong to. Groups are what turns a list of people into permissions: SCIM in backd decides **who is a member**, and the groups the company has pushed decide **what they may do**.

backd is the **SCIM server**. It never calls the identity provider. A company's administrator pastes a tenant URL and a secret token into the provider's console, and from then on joiners, movers and leavers reach backd without anybody touching the organization's members by hand.

Two scopes share one engine:

- **Organization scope:** the people of one organization (B2B). The company's own managers configure it, from the developer's own application (§11).
- **Realm scope:** the users of the realm (workforce apps, internal tools). The realm operator configures it in `realm.yaml`.

What SCIM does **not** do: sign anybody in (that stays org sign-in, [sso.md](./sso.md), or the realm's providers), and it never calls out of backd, so there is no egress and no request to a host chosen by a customer.

Google: Google Workspace's outbound SCIM covers its own app catalog, and whether a custom SAML app can push to an arbitrary SCIM endpoint is not reliable. A Google tenant therefore reaches this feature only if its console offers it, or through an intermediary identity provider. A pull connector (Admin SDK Directory, Microsoft Graph delta) is a different mechanism, a separate later milestone (§13.1).

SCIM depends on **verified domains** (proof, discovery and linking), which are designed in [sso.md §10](./sso.md) and built before SCIM, in the sign-in milestone ([sso.md §14](./sso.md), step S5). `sso_required` is already built.

## 2. Decisions at a glance

| Topic | Decision |
|---|---|
| Role of backd | SCIM 2.0 server for Users and Groups (v1). No client, no pull |
| Architecture | SCIM is a **library** (`scim/`, a public package of this module with an import-guard test) that knows neither backd nor MongoDB: a wire layer, a domain engine, and two ports (`Store`, `Host`) that backd implements. A protocol change touches the wire layer only (§4) |
| Scopes | Organization and realm, one engine, two `Host` implementations (§4.7) |
| Addresses | `/v1/{realm}/_scim/orgs/{org}/v2/…` and `/v1/{realm}/_scim/v2/…`; bearer token, no session |
| Credential | A token generated by backd, shown once, stored hashed, two valid at a time for rotation. Not in `realm.yaml`, not an org secret (§5) |
| Configuration | Policy in `realm.yaml`; the organization's own settings in the database (§6, §7) |
| Who manages (org) | A new capability `manage: scim`, with reauth for changes; a panel in the application, driven by `GET /_orgs/{org}/capabilities` (§11) |
| SCIM id | **The backd user id.** The same person has the same id in every organization that provisions them (§3.1) |
| Roles | **Only from groups.** No default or base roles in SCIM. The owner maps pushed groups, by the provider's group id with the name kept next to it, to roles and teams; a role may have any number of groups; unmapped groups grant nothing (§8) |
| Membership | Being pushed makes a member (no roles of their own). A per-organization setting `membership: mapped` requires at least one mapped group (§8.4) |
| Existing accounts | **No takeover, and no oracle.** In an organization, an email that already has an account is invited, never reported as taken (§3.2). Realm scope may adopt a verified-email account (`on_existing: adopt`) |
| Leaving | Deactivation or delete removes the membership (org) or disables the user (realm). An account SCIM created that has no other membership is disabled too; any other account is never touched (§3.4). SCIM never erases |
| Joining | With SCIM enabled the organization takes in **only provisioned people**: invitations are refused (`409 scim_managed`), and the connection signs in only provisioned people, except holders of `manage: org` (§3.5). No setting |
| Lockout | **Every holder of `manage: org` must have a password and MFA** as backup, enforced when the role is granted and when a credential is removed; roles with `manage: org` cannot be SCIM-mapped. A single manager is a warning (§9) |
| Domains | Provisioned emails must belong to a **verified domain** of the organization ([sso.md](./sso.md)) |
| Hooks | The existing membership hooks and audit; SCIM attributes reach the app through hooks (§10) |

## 3. Semantics

### 3.1 What SCIM creates

A SCIM **link** ties a provider-side person to a backd user inside one scope. The library calls it a `Link` and treats the user as an opaque id; the stored document is in §7.2.

| Field | Notes |
|---|---|
| `id` | the SCIM `id`: **the backd user id** (supplied by the host; the library treats it as opaque). Stable for the person, in this and every other organization |
| `scope` | `realm` or `org:<id>` |
| `external_id` | the provider's `externalId`, unique per scope when present |
| `user_name` | the SCIM `userName` (an email, lowercased) |
| `state` | `pending` (an invitation was sent to an existing account), `active`, `unassigned` (active in the directory, in no mapped group, with `membership: mapped`: not a member), `inactive` (deactivated by the provider), `deleted` (deleted by the provider: hidden, its id answers `404`, kept so that the same person coming back reconnects, purged after the retention period) |
| `display_name`, `attributes` | kept for the hooks and the admin UI, bounded in size; never copied into `users` |
| `created_user`, `disabled_by_scim` | true when SCIM created the account / disabled it, so a reactivation re-enables only what SCIM disabled (§3.4) |
| `granted_roles` | realm scope: the roles SCIM added to `users.roles`, which is a plain list with no per-grant origin; SCIM removes only these (§8.3) |
| `created_at`, `updated_at`, `last_synced_at`, `version` | `version` feeds an ETag in a later version |

Unique on (`scope`, `id`), on (`scope`, `user_name`) and on (`scope`, `external_id`).

**The id is the user id, and that has consequences, accepted:** a provider that provisions a person learns their realm-wide user id; two companies that provision the same person see the same id and can correlate them (a user can belong to up to `max_memberships_per_user` organizations, with one account); and a `201` for an email that already has an account carries that account's id (a new email also returns an id, and a repeated create answers `409`, so it is not an existence test). User ids are not secrets in backd. A link id per organization would avoid all three; the decision was to take the simpler, stable id.

### 3.2 Create (`POST /Users`)

Validation first (below), then in organization scope:

| Situation | Result |
|---|---|
| no user with that email | create the user (no password, no identity, email **unverified**, `created_user`), add the member **with no roles of their own**, create the link `active`. Answer `201`. Roles arrive with the groups (§8). With `membership: mapped` the link is `unassigned` until a mapped group puts them in |
| a user with that email exists | do **not** reveal it. Create the link `pending`, send the existing **organization invitation** (without roles), answer `201`. The person accepts it as any invitation; the link becomes `active` when they join and the roles of their groups apply from then on |
| the user is **already a member** of this organization (joined before SCIM) | link them `active` at once, no invitation: the managers can see their own members, so nothing is revealed. This is how people who joined before SCIM come under it. Holders of `manage: org` are linked like anybody else (their backup, §9, protects them) |
| a `deleted` link of this scope has that email and the user's current email is still it | reactivate it with the same id: new membership, link `active` |
| a link with that email already exists in the scope | `409 uniqueness` (it is this organization's own data) |

The `pending` rule is the crux: a `409` for an existing email would tell any organization's IdP administrator which addresses have accounts anywhere in the realm. The invitation path gives the same answer to "new" and "known", and the known person stays in control: nothing changes for them until they accept. The invitation rules of [organizations.md](./organizations.md) apply (quotas, pending limits, blocked cleared on acceptance), and the email goes through the job queue as for any invitation, so the response time is the same in both cases. The verified-domain requirement also keeps an organization from using this to send invitations to arbitrary addresses. A quota that stops a creation (members per organization, memberships per user, `max_users_per_org`) answers `403 tooMany` and is audited; the realm's sign-up mode (`closed`) does not apply, as the realm switch is the operator's consent (the same reasoning as [sso.md §8](./sso.md)).

In realm scope the operator owns the whole user base, so there is no oracle to protect: an existing email is `409 uniqueness` by default, and `on_existing: adopt` (§6.1) links it **only if the existing user's email is verified in backd**, otherwise `409`.

Validation: `userName` must be a valid email; `emails[primary]`, when present, must equal it; **its domain must be a verified domain of the organization** ([sso.md](./sso.md)); enabling SCIM needs at least one. An address on an unverified or lapsed domain answers `400 invalidValue`. Realm scope uses the operator's `email_domains` list from `realm.yaml` when it is set.

### 3.3 Update (`PUT`, `PATCH`)

- `active`: see 3.4.
- `userName` / `emails`: an email change goes through the same checks as a user's own email change (uniqueness, verified domain); a collision with another account is the generic `409 uniqueness`, which never confirms the other account's existence. v1 refuses such a change.
- `name`, `displayName`, `locale`, enterprise attributes: stored in the link, delivered to the hooks (§10). Only `locale` is copied to the user, and only when the realm lists it.
- Entra's PATCH quirks are handled in the shared layer: `active` as `"True"`/`"False"` strings, operations without `path`, `value` objects.

### 3.4 Deactivate and delete

| Event | Organization scope | Realm scope |
|---|---|---|
| `active: false` | remove the membership, add the user to the connection's `blocked`, revoke the sessions scoped to the organization ([scoped-sessions.md](./scoped-sessions.md) §4.5), link `inactive`. **If SCIM created the account and the person has no other membership, disable the account** (`disabled_by_scim`) and revoke all its sessions | set `users.disabled`, revoke all sessions of the user, link `inactive` |
| `active: true` again | add the member back (the organization's own IdP decides, which counts as the invitation), clear `blocked`, link `active`, recompute roles from groups; **re-enable the account only if `disabled_by_scim`** | clear `disabled` if SCIM set it, recompute roles |
| `DELETE` | as deactivation, then the link becomes `deleted` | disable the user (never erase), the link becomes `deleted` |

SCIM never erases accounts. An account that existed before SCIM touched it is never disabled (it may hold personal data outside the organization); it only loses the membership. An account an administrator disabled stays disabled when SCIM reactivates the person. Erasure stays an administrator and compliance action.

Removing a member who holds `manage: org` is subject to the existing `last_org_manager` guard: if they are the last manager SCIM gets `409` (§9).

Roles added by hand (an owner promoted in backd, a timed grant) survive updates: SCIM only manages the grants it made (those that come from group mappings, marked `source: scim`) and never removes a role it did not grant.

### 3.5 Signing in to a SCIM-managed organization

Enabling SCIM makes the organization **scim-only**, with no setting. The identity provider's token proves the person; SCIM says whether they belong:

- **Through the connection**, a person signs in to the organization only if they hold an `active` link, or hold `manage: org`. The connection does **not** create a member on first sight (the join rule of [sso.md §8](./sso.md) is off while SCIM is enabled). This closes the loophole where a deprovisioned person signs in again and re-joins by themselves.
- **No other way in.** While SCIM is enabled, an organization takes in **only provisioned people**. `POST /_orgs/{org}/invitations` answers `409 scim_managed` for everybody, managers included, and the invitations that were still pending when SCIM was enabled are revoked (the answer to enabling lists how many). The one invitation that still exists is the one SCIM itself sends to an existing account (§3.2), because it is part of provisioning. A new manager is therefore a provisioned member who is promoted by role change (`PATCH …/members/{user}`), and the backup rule of §9 applies to the promotion.
- **Holders of `manage: org` keep every method:** password with MFA, magic link or the connection. That is their backup (§9), so a broken integration never locks the organization out.
- **Everyone else's other methods** (password, magic link) are governed by the separate `sso_required` switch ([scoped-sessions.md](./scoped-sessions.md) §6, amended: its exemption for managers, §9.6).
- **Binding the first sign-in to a SCIM-created user:** a user SCIM created has no identity. The first sign-in through the connection binds the identity to the link whose `user_name` equals the **verified email** of the token, **in the same organization and only for a user SCIM itself created that has no identity on the connection**. Its safety rests on the tenant/Workspace restriction of the connection (the person is proven to belong to the company), the Microsoft rule that email counts only on the UPN domain, the verified domain of that email, and that the target account was created by this organization's SCIM, so there is no pre-existing account to take over. A `pending` link (an existing account) is never bound by SCIM: the person accepts the invitation, or the verified-domain linking of [sso.md](./sso.md) applies.
  - *Option:* `bind_by: external_id` binds by the token's stable claim (`oid` for Microsoft, `sub` for Google) when the administrator maps `externalId` to it: no email trust, but it needs a correct attribute mapping on the provider side. `email` is the default because Entra's default `externalId` is not the object id.

### 3.6 What SCIM cannot do

It cannot grant a role the configurer could not grant, nor any role that holds `manage: org`, cannot change the organization (settings, roles, teams), cannot read or write documents, and cannot see anybody who is not in its scope.

## 4. Architecture: a library and a thin backd side

SCIM is a protocol; backd's users, organizations, roles and sessions are not. They are kept apart on purpose: **the SCIM code is a library that knows neither organizations nor MongoDB nor HTTP routing of backd**, and backd plugs into it through interfaces the library defines. A change of the protocol (a new revision, an Entra or Okta quirk, SCIM 1.1) touches the wire layer only; a change in how backd stores or grants things touches the backd side only.

### 4.1 Layers

```
scim/                        the library; imports nothing from backd (a test enforces it)
├── wire/v2/                 the protocol: RFC 7643/7644 JSON <-> wire types
│     user.go group.go list.go patch.go filter.go error.go discovery.go
│     dialect/               provider quirks (entra, okta): normalize what arrives into domain changes
├── (root package scim)      the domain and the engine
│     Person, Group, Link, Change, Scope, Outcome      protocol-agnostic types
│     Engine                 the use cases: create, replace, change, deactivate, delete,
│                            list/get, group create/change/delete, member add/remove
│     Store                  port: persistence of links and groups          (implemented by backd)
│     Host                   port: what the application does about it       (implemented by backd)
│     errors.go              ErrConflict, ErrNotFound, ErrTooMany, ErrProtected, ErrInvalid{Field}…
├── httpscim/                a net/http handler: routing, content negotiation, calls wire + Engine
│                            (authentication is a hook the host supplies)
└── scimtest/                a conformance suite for Store, and fakes (in-memory Store, recording Host)

backd side
├── internal/mongodb/scim.go           Store over scim_links, scim_groups, scim_scopes
├── internal/auth/scim_org.go          Host for an organization scope: members, invitations, roles, sessions
├── internal/auth/scim_realm.go        Host for the realm scope: users, roles, sessions
├── internal/auth/scim_tokens.go       token creation, hashing, verification, rotation
├── internal/registry/scim.go          the realm.yaml sections (§6)
└── internal/httpapi/scim.go           mounts httpscim, the token hook; the management API (§11)
```

The library starts as a **public package `scim/` in the same module**, with a test (`go list -deps`) that fails if it imports anything under `github.com/fernandezvara/backd`. That gives the isolation without a second repository, and it can move to its own module (as `kli` did) with no code change.

### 4.2 The domain the library speaks

Everything inside the engine is in terms of protocol-free types:

| Type | Meaning |
|---|---|
| `Scope` | an opaque string chosen by the host (`realm`, `org:<id>`); the library never parses it |
| `Person` | `ID` (opaque, supplied by the host: for backd, the user id), `UserName`, `ExternalID`, `Active`, `DisplayName`, `Emails`, `Locale`, `Attributes` (bounded map) |
| `Group` | `ID`, `ExternalID`, `DisplayName`, `Members []PersonID` |
| `Link` | `Person` plus `Scope`, `State` (`pending`, `active`, `unassigned`, `inactive`, `deleted`), flags the host sets, timestamps, `Version` |
| `Change` | a protocol-free edit: `Set(field, value)`, `Clear(field)`, `AddMember(id)`, `RemoveMember(id)`. A SCIM PATCH, a PUT diff and an Entra quirk all become a list of `Change` |

### 4.3 The two ports

```go
// Store persists what the library owns. backd implements it over MongoDB.
type Store interface {
    LinkByID(ctx, scope, id) (Link, error)
    LinkByUserName(ctx, scope, userName) (Link, error)
    LinkByExternalID(ctx, scope, externalID) (Link, error)
    ListLinks(ctx, scope, Query) ([]Link, int, error)        // Query: filter, start, count
    PutLink(ctx, Link, expectVersion int) error               // ErrConflict on a lost race
    DeleteLink(ctx, scope, id) error
    GroupByID / GroupByExternalID / ListGroups / PutGroup / DeleteGroup   // the same shape
    GroupsOf(ctx, scope, personID) ([]Group, error)
}

// Host is what the application does when a directory change arrives. backd implements it twice
// (organization, realm). Every method is idempotent: the provider retries.
type Host interface {
    // Provision decides what a new person is. The host owns the "exists elsewhere" policy (§3.2).
    Provision(ctx, scope, Person) (Outcome, error)            // Outcome: ID + State (Active | Pending | Unassigned)
    Update(ctx, scope, Link, []Change) error                  // profile changes the host cares about (email, locale)
    Deactivate(ctx, scope, Link) error                        // org: remove member, block, revoke, maybe disable; realm: disable
    Reactivate(ctx, scope, Link) error
    Remove(ctx, scope, Link) error                            // delete: as deactivate, host decides the rest
    Guard(ctx, scope, Link, Action) error                     // last_org_manager, protected admin roles (§9): ErrProtected
    GroupChanged(ctx, scope, Group, added, removed []PersonID) error   // host recomputes roles (§8.3)
    Limits(ctx, scope) Limits                                 // MaxPeople, MaxGroups, MaxMembers, Retention
}
```

What decides where a rule lives:

- **In the library:** SCIM semantics. Parsing and rendering, filters, PATCH application (path and pathless, Entra's string booleans), pagination, `uniqueness` conflicts inside a scope, the link state machine, `version`-based optimistic concurrency, group membership bookkeeping, SCIM error mapping, `ServiceProviderConfig`/`Schemas`/`ResourceTypes`, idempotent replays.
- **In backd (through `Host`):** everything that is a backd concept. Whether an email already has an account and what to do (invite, link, conflict), memberships, `blocked`, roles and teams from mappings, sessions, the manager backup rule, quotas, audit, hooks, verified domains.
- **Never in the library:** a token (the HTTP hook authenticates and returns the `Scope`), a role, an organization, a Mongo type.

### 4.4 Where the wire stops

The `httpscim` handler does: authenticate (host hook) → `wire` decodes the request into a domain `Person`/`[]Change` → `Engine` runs the use case against `Store` and `Host` → `wire` encodes the domain result or error. The engine never sees JSON or HTTP; `wire` never sees `Store` or `Host`.

| Wire (RFC 7643) | Domain (`scim.Person`) | Stored (`scim_links`) |
|---|---|---|
| `id` | `ID` | `user` (inside `_id`) |
| `externalId` | `ExternalID` | `external_id` |
| `userName` | `UserName` | `user_name` |
| `active` | `Active` | `state` (`active`, `unassigned` ↔ `true`; `inactive`, `deleted` ↔ `false`) |
| `displayName`, `name.formatted` | `DisplayName` | `display_name` |
| `emails[type=work\|primary].value` | `Emails` | inside `attributes.emails` |
| `locale` | `Locale` | `attributes.locale` |
| `meta.created`, `meta.lastModified`, `meta.version` | `Created`, `Modified`, `Version` | `created_at`, `updated_at`, `version` |
| enterprise extension | `Attributes["enterprise"]` | `attributes.enterprise` |

A second wire version is a second package beside `wire/v2` that fills the same domain types; the engine and both ports do not change. A provider quirk is a `dialect` that rewrites its odd input into `Change`s before the engine sees it.

### 4.5 Consistency and retries

The `Store` and the `Host` are not one transaction (the host changes members and roles; the store changes links). Rules that make that safe:

- The engine orders effects so that a repeat is harmless: it calls the `Host` first (idempotent), then writes the link with the expected `Version`. A crash between them is repaired by the provider's next cycle, which replays the same request.
- `Provision` is keyed by (scope, `userName`): a replay finds the link or the host's own result and returns the same answer.
- Group recomputation is not done inline for large groups: `GroupChanged` returns quickly after queueing a recompute job for the affected people (backd's existing job queue); the job is idempotent and resumable.
- A quota or a protection stops the request with a library error (`ErrTooMany`, `ErrProtected`), which `wire` renders as the SCIM error.

### 4.6 Tests

The library is tested alone: golden files from the RFC examples and sanitized traffic from Entra and Okta for `wire` and `dialect`, the engine against `scimtest` fakes, and `scimtest.TestStore` as the suite every `Store` implementation (backd's Mongo one included) must pass. The backd side is tested with the Host implementations and the real MongoDB, plus the contract test for the management endpoints. Entra's own "validate" tool is the manual acceptance.

### 4.7 Organization and realm: the two Hosts

| | Organization `Host` | Realm `Host` |
|---|---|---|
| Anchor | `scim_scopes` document of the org | `scim:` section of `realm.yaml` (tokens in `scim_scopes`, `_id: realm`) |
| Create | user + membership + link | user + link |
| Roles | from mapped groups; the mapper must hold what they map (granting rules) | from groups mapped in `realm.yaml` |
| Deactivate | remove member, block, revoke org sessions; disable a SCIM-created account with no other membership | disable user, revoke sessions |
| Existing email | invitation (`pending`), or link when already a member | `409`, or adopt a verified-email account |
| Sign-in binding | org connection | realm provider |
| Guard | `last_org_manager` and the manager backup rule (§9) | users holding a role with admin rights are never changed by SCIM |

## 5. Tokens

- **Format:** `scim_` + 32 random bytes (base32). A prefix of the first characters is shown in lists. Stored as `HashToken(token)` (the API-key hashing, `internal/auth/apikeys.go`). Never logged, never returned after creation.
- **Per scope:** up to 2 active at a time. Creating a second is the rotation: the provider is switched, then the old one is revoked. Optional `expires_at`.
- **Verification:** constant-time compare of the hash on every request; the token determines the scope, so the `{org}` (the id) in the path must match or the answer is `401` (same answer as a bad token, so nothing says whether an org exists or has SCIM).
- **Networks:** an optional allow-list of source networks per scope, as API keys have; empty by default because provider IPs change.
- **Not an org secret:** org secrets are sealed and readable by the server; this must be verifiable but never recoverable, which is what a hash gives.
- **Lifecycle:** deleting the organization, disabling SCIM or losing the capability that configured it (same re-check as `join_roles`) stops the token working at once.

## 6. Configuration in `realm.yaml`

The realm file says **what is allowed and how far it may go**; the data of each organization lives in the database (§7).

### 6.1 Realm scope

```yaml
# The realm's own users, pushed by the realm's identity provider.
scim:
  enabled: true
  provider: microsoft            # realm sign-in provider the first sign-in binds to
  email_domains: [acme.example]  # optional; when set, every provisioned email must match
  protected_roles: [support]     # more roles whose holders SCIM never changes (admin-right roles always are)
  on_existing: conflict          # conflict | adopt (adopt links an existing user only if their email is verified)
  bind_by: email                 # email | external_id
  max_users: 10000
  max_groups: 500
  deleted_retention: 90d         # how long a deleted person is remembered, so a return reconnects
  rate_limit: { limit: 600, window: 1m }

# The realm's own roles, mapped to the provider's groups (realm scope).
roles:
  editor:
    description: Writes, publishes and decides who can read the pages
    scim_groups:                 # by the provider's group id; the name is a label
      - { id: "9b1c0f6e-5f0e-4a6e-8f7d-0a1f6c2d3e44", name: Editors }
      - { id: "c47a2d90-1b3e-4f55-9a0c-6d7e8f901234", name: Editors EU }
  contributor:
    description: Writes drafts and edits pages, usually for a period
    scim_groups:
      - { id: "5d0e8a77-2c19-4b63-b1f4-3e9a7c6d5b20", name: Contributors }
```

- `enabled` defaults to `false`; with it off the whole surface answers `404`.
- There is **no `default_roles`**: a user SCIM creates holds no role of its own; roles come only from the groups. A role without `scim_groups` can never be granted by SCIM, so listing groups is the operator's decision, role by role. Several groups may feed one role and one group may feed several roles.
- `id` is the group's id in the provider (`externalId` of the SCIM group; in Entra the object id); `name` is only a label for logs and the admin UI, and when the provider renames the group the stored name follows, while the mapping, which is by id, keeps working. **Mappings are by id only**: a group the provider sends without an `externalId` cannot be mapped.
- **A role with `admin` rights (`admin: true`, `read` or a list) cannot have `scim_groups`**: that would let the identity provider grant access to the admin API. Checked at load. Users holding such a role are protected by default; `protected_roles` adds more.
- Every role with `scim_groups` must be declared. All checked at load, with a message that names the key.
- Tokens are created with `backd scim token` (§11), not in this file.

### 6.2 Organization scope (the realm's switch)

```yaml
organizations:
  roles:
    owner: { manage: [org, members, roles, teams, sso, scim, domains] }
    member: { description: Everyone in the organization }
  # Roles held within one team: what groups usually mean ("Platform editors").
  team_roles:
    editor:
      description: Writes, publishes and decides who can read the team's pages
      scim: true             # an organization may map groups to this team role
    contributor:
      description: Writes drafts and edits the team's pages, usually for a period
      scim: true
  scim:
    enabled: true          # the realm lets organizations set up SCIM
    max_users_per_org: 5000
    max_groups_per_org: 500
    max_mappings_per_org: 100
    deleted_retention: 90d
    rate_limit: { limit: 600, window: 1m }   # per token
```

- With it off, `/_scim/orgs/…` and `/_orgs/{org}/scim` answer `404`, as `organizations.sso` does.
- The capability name is `scim` (`CapSCIM` in `registry.OrgCaps`, which is a `uint8` with room for it; `AllCaps` includes it, so the administrator paths that pass `AllCaps` can configure SCIM). `domains` is the capability of [sso.md](./sso.md).
- **`scim: true` on a role** (an organization role under `roles`, or a team role under `team_roles`) says that organizations may map groups to it; the mapping itself is each organization's, made by its owner **after** the provider has pushed the groups (§8), because group names and ids belong to the company's directory, not to the realm. A role without it cannot be reached by SCIM. **A role that holds `manage: org`, directly or through a team role, cannot have `scim: true`** (checked at load): the people who run the organization are never made by the directory.
- The realm's own `organizations.default_roles` is not SCIM's: every member holds it whatever SCIM does. Enabling SCIM with a non-empty list is allowed; the status warns about it (§9.5).
- Enabling SCIM or `sso_required` needs the realm to offer **password sign-in and MFA** (the backup of §9); otherwise it answers `409 backup_unavailable`.

## 7. Persistence

Auth data, so in the realm's system database, like `org_connections`. Three new collections, created and validated by `backd provision` as the others are (`$jsonSchema` validator, indexes in `systemCollection`), and two small changes to `org_members`.

### 7.1 `scim_scopes`: the settings of one scope

One document per scope: `_id` is `org:<org id>` for an organization and `realm` for the realm. The realm document carries only the tokens and runtime state (its policy is in `realm.yaml`, §6.1); an organization document carries its whole configuration.

| Field | Notes |
|---|---|
| `_id`, `org` | `org:<id>` and the organization id; the realm document has `_id: realm` and no `org` |
| `enabled` | off keeps the data and the tokens but answers `403 scim_disabled` |
| `membership` | `any` (default) or `mapped` (§8.4) |

| `provider` | the connection (`google`/`microsoft`) the first sign-in binds to; optional when the organization has no connection |
| `tokens` | up to 2 of `{id, prefix, hash, created_at, created_by, expires_at, last_used_at}`. The hash is a multikey unique index, so a request finds its scope from the token. `last_used_at` is written at most once a minute (as API keys do) |

```json

  "state": "active",
  "display_name": "Ana López",
  "attributes": { "locale": "es", "emails": [{ "value": "ana@acme.example", "primary": true }], "title": "Editor" },
  "created_user": true,
  "disabled_by_scim": false,
  "granted_roles": [],
  "version": 4,
```

- The SCIM `id` is `user`, the backd user id. `state` is one of `pending`, `active`, `unassigned`, `inactive`, `deleted`.
- `granted_roles` is used by the realm scope only (§8.3). `attributes` is bounded (16 KiB).
- A `deleted` link drops `user_name` and `external_id` into `former_user_name` and `former_external_id`, so the unique indexes free them and the same person reconnects with the same id (§3.2); a retention job purges `deleted` links after `deleted_retention` (default 90 days), and erasure removes the links of the user.
- Indexes: (`scope`, `user_name`) unique sparse; (`scope`, `external_id`) unique sparse; (`scope`, `user`) unique; (`scope`, `former_user_name`); (`user`) for erasure and export; (`scope`, `state`) for counts and the purge.

### 7.3 `scim_groups`: a pushed group

```json

  "created_at": "2026-11-02T09:41:00Z",
  "updated_at": "2026-11-05T07:00:12Z"

```

- `members` are user ids (the SCIM ids of the people), at most 5000 per group (a document of about 150 KB at most).
- `display_name` follows renames; `mappings[].group` refers to `external_id` and never changes.
- Indexes: (`scope`, `external_id`) unique sparse; (`scope`, `members`) multikey, to find the groups of a person.

### 7.4 Changes to existing collections

`org_members` keeps its shape. The grant documents inside `roles` and `team_roles` (`grantDoc` in `internal/mongodb/orgs.go`) gain two optional fields, so no migration and no new validator rule:

```json
{ "role": "editor", "granted_at": "2026-11-05T07:00:12Z", "source": "scim", "groups": ["9b1c0f6e-5f0e-4a6e-8f7d-0a1f6c2d3e44"] }
```

`auth.RoleGrant` gains `Source string` and `Groups []string` with the same names (`TeamRoleGrant` embeds it). A grant without `source` is a hand-made one, as today. `org_connections` is unchanged (`blocked` is reused). `users` gains nothing for SCIM; its `disabled` flag is reused. `identities` is unchanged. The job queue gets one kind, `scim.recompute`. `org_domains` and its changes are in [sso.md](./sso.md).

### 7.6 Export, import, deletion

- **Export and import:** `scim_scopes` (with its mappings), `scim_links` and `scim_groups` are auth parts (`--include auth`); **token hashes do not travel**, so after an import every token must be created again; links travel with their users (a user not in the package drops its link). Anonymized packages blank `user_name`, `external_id`, `display_name` and `attributes`.
- **Deleting the organization** removes `scim_scopes`, its tokens, its links and its groups in the existing resumable job.

## 8. Groups and role mapping

Groups are how a company says what people may do, so they are part of v1. SCIM decides **who is a member** (§3); the groups decide **what roles and teams they hold**. There are no default roles in SCIM.

### 8.1 What is stored

`scim_groups` (§7.3): the provider's group id as `external_id` (in Entra the object id; unique per scope; a group without one is stored but **cannot be mapped**, and the admin UI says why), the current `display_name` (refreshed on every update) and `members` as user ids.

Every pushed group is stored, up to `max_groups`, so the owner can see it and map it; a group nobody maps grants nothing ("ignored" means ignored for roles, not dropped). Over the cap, `POST /Groups` answers `403`/`tooMany` and is audited.

### 8.2 Mappings

A **mapping** says that holding a group means holding a role or a team seat:

| Field | Notes |
|---|---|
| `group` | the group's `external_id`. The mapping is **by id**, so a rename in the directory changes `display_name` and nothing else |
| `name` | the group's name when the mapping was made, shown with the current one; refreshed when the group is renamed. A label, never a key |
| `role` | an organization role that has `scim: true` in `realm.yaml` (§6.2) |
| `team`, `team_role` | alternatively, membership of an organization team, optionally with a role held within it. `team_role` must be a team role with `scim: true`; with `team` alone the mapping is plain membership. Most real groups ("Platform editors") are this form |

- **Many to many:** one role may have any number of groups (`editor` ← Editors, Editors EU) and one group may appear in several mappings.
- **Who maps:** the organization's owner (`manage: scim`) after the groups have been pushed, picking from the stored list (`GET …/scim/groups`) through the application's panel, the admin UI, the API or the CLI. Mapping a group that does not exist (yet) is refused: the id must be a stored group with an `external_id`.
- **Bounds:** a role without `scim: true` cannot be mapped, and no role that holds `manage: org` can have it; the mapper must hold the role they map (the granting rules of `join_roles`); at most `max_mappings_per_org`. Changes are audited (`org.scim.mapping_set`, `…_deleted`) with the group id and name.
- **Stale mappings:** if the realm later drops `scim: true` from a role, or removes the role, the mapping stays visible with a warning and grants nothing from the next recompute.
- **Realm scope** has the same mapping, written by the operator on the role in `realm.yaml` (`scim_groups: [{id, name}]`, §6.1), and checked at load.

### 8.3 Computing roles

A member's SCIM roles are the union of the roles (and team seats) of every mapped group they belong to. They are stored as ordinary grants marked `source: scim`, with the mapped groups as their origin so the admin UI can say "editor, through Platform editors". Recomputation happens, per affected member:

- when a group's members change (`PATCH`/`PUT` of the group, or a user added or removed from it);
- when a mapping is created, changed or removed: a resumable job recomputes the members of the organization (bounded by `max_users_per_org`);
- when a user is added back after a deactivation, or a `pending` link becomes `active`;
- when a group is deleted by the provider (its members lose what only it gave them).

In organization scope the grants are `RoleGrant`s of the member (`direct` roles) and gain a `source` field (`scim`, with the group ids); a team seat uses the same field in `TeamRoleGrant`, which embeds it. In realm scope `users.roles` is a plain list, so SCIM only adds a role that is not already there and records it in the link's `granted_roles`; it removes only roles it recorded, so a role an administrator also gave by hand is never taken away.

Hand-made grants are never touched, including timed ones: a hand-made `contributor` window and a SCIM `contributor` through a group are two grants, and the role is held while either counts. Removing the last source removes the role, never the member.

### 8.4 Ordering, and members with no mapped group

Providers push users, then groups and their members. A mapping needs the groups to exist, so on a new setup the sequence is: the provider pushes users and groups, the owner maps, the job grants. Until then the members hold no SCIM roles. A group pushed with a member that is not yet a link (a user the provider has not sent) answers `400 invalidValue`, and the provider retries on its next cycle.

`membership` decides what a pushed person with **no mapped group** is:

- `any` (default): a member with no SCIM roles (the realm's `default_roles` still apply, as to every member).
- `mapped`: not a member. Their link is `unassigned`; they become a member when a mapped group takes them in and stop being one (membership removed, **not** blocked, link back to `unassigned`) when the last mapped group lets them go. Least privilege, at the price that people appear and disappear as mappings change.

Switching the setting runs the recompute job, and the answer to `PUT` says how many members it removes.

### 8.5 Managers and groups

Roles that hold `manage: org` cannot be mapped (§6.2), so a group sync never grants or takes away the power to run the organization. A manager who is also in the directory is linked like anybody else (§3.2); their groups give them only the other roles. If the provider deactivates them, §3.4 applies, subject to `last_org_manager`.

## 9. Lockout protection (applies with and without SCIM)

### 9.1 The rule: every manager has a backup

> **Every holder of `manage: org` must have a password and a second factor enrolled.** A second factor is an enrolled MFA method or a passkey.

"Holder" is whoever has the capability now: through a direct role, a team role, or the realm's `default_roles`. These are the people who can still sign in when the integration fails (the identity provider is down, the connection secret expired, SCIM deactivated the wrong people), because managers keep every sign-in method (§3.5). This replaces the earlier idea of a fixed number of recovery members: instead of counting, every manager is made able to recover.

The rule applies **always**, with or without SCIM or `sso_required`, to organizations of a realm that offers password and MFA; a realm that offers neither an MFA method nor passkeys, or no password sign-in, cannot enable SCIM or `sso_required` (`409 backup_unavailable`) and keeps today's behaviour otherwise.

### 9.2 Enforcement

| Moment | Behaviour |
|---|---|
| granting a role or team seat that gives `manage: org` (member roles, team roles, team membership, invitation roles) | refused `409 backup_required` if the person lacks a password or MFA; the body names what is missing |
| a manager removing their password or their MFA, or an administrator doing it for them | refused `409 backup_required` while they hold `manage: org` |
| enabling `sso_required` or SCIM | refused `409 backup_required` listing the managers that lack a password or MFA |
| removing a manager, changing roles, team changes, leaving | the existing guard: `409 last_org_manager` if nobody with `manage: org` would remain (`keepManagerWith`, `internal/auth/orgs.go`) |
| SCIM deactivate or delete of a manager | applied, subject to `last_org_manager` |
| disabling or erasing an account | allowed; the last-manager check counts only managers who are usable (not disabled, not erased) |

Existing organizations are not rewritten: a manager without a password or MFA stays, the status warns (§9.5), and the rule applies to the next grant or credential change.

### 9.3 Enrolment

Granting `manage: org` to someone without a backup is refused with a body the panel can act on (`missing: ["password","mfa"]`). The sensible flow is the person sets a password and enrols MFA first (both exist), then the grant is made. An invitation that carries a manager role is refused the same way when the invited account is new, so the first owner of a new organization (who created it with a password) already complies.

### 9.4 Realm scope

Users holding a role with admin rights are never changed by SCIM (§6.1). Admin-right roles already require a second factor in the realm's own settings, as in the Shelf. The operator's break glass (`backd` with the environment bootstrap credentials) remains.

### 9.5 Visible state

`GET /_orgs/{org}` gains `warnings`, a list the panel can show:

| Warning | Meaning |
|---|---|
| `single_manager` | the organization has one manager: a lock or deletion of that account leaves only a realm administrator able to recover. Warning only, by decision |
| `manager_without_backup` | a manager (grandfathered) has no password or no MFA |
| `default_roles_nonempty` | `organizations.default_roles` is held by every provisioned member |
| `members_without_link` | members that SCIM does not manage (listed by `members?scim=false`) |
| `stale_mappings` | a mapping points at a role the realm no longer lets organizations map |

### 9.6 Changes to other designs

- [scoped-sessions.md §6](./scoped-sessions.md) (`sso_required`): password, magic link and reset for **holders of `manage: org`** stay allowed; the break glass of realm administrators remains. The requirement that the person enabling it has signed in through a connection becomes the backup rule of §9.1.
- [sso.md §8](./sso.md): the join rule is off while SCIM is enabled for the organization (§3.5), and email linking has the verified-domain rule of [sso.md §10.4](./sso.md).
- There is no milestone 31 any more: [sso.md §14](./sso.md) replaces it. Generic OpenID Connect (#157, #599) is steps S3 and S6, verified domains and discovery (#601) step S5, and #598 (Apple for organizations) is closed as won't-do. #600 (`sso_required`) was closed by milestone 34. The local issue files under `support_docs/issues/` and the GitHub issues are updated when this milestone's issues are created, not by this document.

## 10. Hooks, audit, observability

- **Hooks:** the membership hooks ([organizations.md](./organizations.md), `OrgHooks`) already run through the job queue; SCIM calls them with `by: scim` and the link attributes (`display_name`, `attributes`) so an app can build a profile document. Decided: hooks only, no new trigger event.
- **Audit:** `org.scim.set`, `org.scim.disabled`, `org.scim.token_create`, `org.scim.token_revoke`, `org.scim.user_create`, `…_update`, `…_deactivate`, `…_delete`, `org.scim.mapping_set`, `…_deleted`, `org.scim.protected`, `org.scim.invited`, `org.scim.bulk_guard`; realm scope `scim.*`. The actor is the token (`prefix`), never its value; no bodies.
- **Logs:** never request bodies, emails or tokens (SCIM bodies are personal data); the usual request log line with the route and status.
- **Metrics:** requests by status, links by state, last successful request per scope.
- **Errors** use SCIM's error schema (`urn:ietf:params:scim:api:messages:2.0:Error`, `scimType`: `uniqueness`, `invalidValue`, `invalidSyntax`, `mutability`, `tooMany`) with the HTTP status; the codes of §9 appear in `detail`.

## 11. API, CLI, clients and the self-service panel

**SCIM endpoints** (token): `GET|POST /Users`, `GET|PUT|PATCH|DELETE /Users/{id}`, `GET|POST /Groups`, `GET|PUT|PATCH|DELETE /Groups/{id}` (member add/remove by PATCH, as Entra sends it), `GET /ServiceProviderConfig`, `GET /Schemas`, `GET /ResourceTypes`. `filter` supports `userName eq`, `externalId eq` on users and `displayName eq`, `externalId eq` on groups; paging by `startIndex`/`count` (max 100); no Bulk, no sort, no ETag in v1. `Content-Type` `application/scim+json` accepted and sent.

**Management** (a session with `manage: scim` and reauth, like `sso`):

- `GET /v1/{realm}/_orgs/{org}/scim` (settings, `scim_url` to paste, token prefixes, counts, `warnings`, `mappable_roles`)
- `PUT /v1/{realm}/_orgs/{org}/scim`
- `POST /v1/{realm}/_orgs/{org}/scim/tokens` (answers the token **once**), `DELETE …/tokens/{id}`
- `GET /v1/{realm}/_orgs/{org}/scim/users` (links with state and the roles they hold through groups, for the admin UI and the panel)
- `GET /v1/{realm}/_orgs/{org}/scim/groups` (stored groups: id, name, member count, whether mapped), `GET|PUT /v1/{realm}/_orgs/{org}/scim/mappings` (the whole list, validated as one; answers how many members the change affects)
- **`GET /v1/{realm}/_orgs/{org}/capabilities`** → `{ "can": ["org","members","roles","teams","sso","scim","domains"] }`: what the caller may do in that organization (the org answers carry role names only, so a client cannot tell otherwise). Decided: a separate endpoint, not a field on the org answers. Any member may call it; it reveals only the caller's own capabilities.
- the same under `/v1/{realm}/_admin/orgs/{org}/scim`, and `/v1/{realm}/_admin/scim` for the realm scope

**CLI:** `backd orgs scim`, `scim-set`, `scim-token`, `scim-token-revoke`, `scim-groups`, `scim-map`; `backd scim token`, `scim token-revoke`, `scim status` (every value is a flag, single-word subcommands as the existing ones).

**Clients and UI:** an organization page tab "Provisioning" in the admin UI (tenant URL, token, verified domains, warnings, the links and their state, the pushed groups with a role/team picker for the mappings); a typed helper in the JS and Dart clients (`orgs.scim.get/set/createToken/groups/setMappings`, `orgs.capabilities`). Nothing for the provider's side beyond docs.

### 11.1 Self-service: the same API serves the application's own panel

There are two ways to configure SCIM, and they are the same management API:

| Who | How | Where |
|---|---|---|
| The developer or operator of the realm | `backd orgs scim…`, `backd scim…`, `/_admin/orgs/{org}/scim`, the admin UI | their own terminal and the admin UI; for any organization |
| **The administrators of a customer's organization** | `/_orgs/{org}/scim…` with their own session, from **a panel in the developer's application** | one organization, only what their roles allow (`manage: scim`) |

The second is the product: a company's IT administrator, signed in to the application, opens "Settings → Provisioning" and does everything without the developer or the operator. The developer builds that panel with the JS or Dart client; the backd admin UI's organization page is the reference implementation (`ui/admin/src/views/OrgView.vue`), and the panel needs nothing the admin UI does not already use. Organization sign-in connections ([sso.md](./sso.md)) and verified domains work the same way, so the documentation treats them together (§11.5).

### 11.2 What a panel is made of

| Screen | Calls | Notes for the panel |
|---|---|---|
| Status | `GET /_orgs/{org}/scim` | `enabled`, `scim_url` (the tenant URL to paste, built from `email.public_url`/`BACKD_URL`), token prefixes and `last_used_at`, counts by state, `warnings`, `mappable_roles` |
| Domains | `GET/POST/DELETE …/domains` | the DNS record to create and its state ([sso.md](./sso.md)) |
| Set up | `PUT …/scim` | `membership`, `bind_by`, `provider`. The answer is the whole document. `409 backup_required` carries what is missing |
| Token | `POST …/scim/tokens`, `DELETE …/tokens/{id}` | the token is in **this answer only**: the panel shows it once, with a copy button and a warning, and never stores it. Reauth needed |
| Groups | `GET …/scim/groups` | every pushed group, with `mapped`, member count and whether it has an `external_id` |
| Mappings | `GET/PUT …/scim/mappings` | a group → role or team picker. `mappable_roles` lists only the roles that have `scim: true` **and** that the caller may map, so the picker never offers an invalid choice. The answer says how many members the change affects |
| People | `GET …/scim/users`, `GET …/members?scim=false` | linked people with state and the roles they hold through groups; and the members SCIM does not manage yet, so the admin can see who is outside it |
| Backup | `warnings` and the members' `mfa`/password state | a warning with the exact fix ("this manager needs a password and MFA") and a link to the members screen |

Rules every panel has to follow, all of them already how backd answers:

- **Show what the caller may do.** Call `GET /_orgs/{org}/capabilities` and hide what is absent.
- **Ask for a fresh proof for changes.** `PUT` and token calls answer `403 reauth_required`; the client wraps them in `client.auth.withProof(…)`, as for `sso`.
- **Secrets and tokens are write-only.** Nothing the panel can read returns the token or a client secret; the panel must not keep the token after showing it.
- **Render the errors the API gives:** `backup_required`, `backup_unavailable`, `scim_disabled`, `scim_managed` (invitations are off while SCIM is on: hide the invite button), `tooMany`, `forbidden`, `last_org_manager`. They carry the data to explain themselves.
- **Do not assume the feature exists.** The whole surface answers `404` while the realm has `organizations.scim` off; the panel hides the section.

## 12. Security considerations

- **No oracle:** an existing email is invited, never reported; a duplicate create answers a generic `409`; a wrong token, a wrong org and a disabled SCIM all answer `401`/`404` the same way. The SCIM id is the user id (accepted, §3.1): it reveals the id of an account that already exists, never that it exists.
- **Takeover:** SCIM never links to an existing account; the single sign-in binding (§3.5) is restricted to accounts SCIM created, in the same organization, behind the tenant/Workspace restriction, the Microsoft UPN rule and a verified domain. Linking an existing account by verified domain is [sso.md](./sso.md)'s rule, with its own conditions.
- **Squatting:** provisioned emails must belong to a **verified domain** of the organization; unverified emails of SCIM-created accounts cannot sign in by themselves, and the person who truly owns the address proves it by email and then owns the account. A lapsed domain stops provisioning at once.
- **Privilege:** only roles marked `scim: true` by the realm can be mapped, and never one that holds `manage: org`; the mapper must hold them (granting rules). A group named like an admin group in the directory grants nothing until the owner maps its **id**; mappings are by id, not name, so a renamed or look-alike group can't inherit a role. Re-checked by the "setter lost the role" disable.
- **Blast radius:** a stolen token can create, deactivate and update users of one scope, up to `max_users`. It cannot grant a manager role, cannot read any data, cannot change settings. Rotation, `expires_at`, the network list and the rate limit are the controls.
- **Deprovisioning latency:** providers sync on a cycle (Entra: about 40 minutes), so SCIM is not an instant revocation. Docs say so and point to `session_max_age`, `sso_required` and the on-demand provisioning button.
- **Availability:** a misconfigured provider can deactivate every user; the manager backup (§9) keeps the organization manageable, and `max_users` plus a **bulk-deactivation guard** (refuse a burst that would remove more than half of the active links in an hour, `429 scim_bulk_guard`, audited as `org.scim.bulk_guard`, clearable by an administrator) limit the damage.
- **Privacy:** SCIM data is personal data: it is in the export and erasure of the user, and in the retention rules ([compliance.md](./compliance.md)); the link of an erased user is deleted; `deleted_retention` bounds how long a leaver is remembered.
- **Update the security pages** in the same milestone: `docs/content/docs/operate/administration/security.md` and `SECURITY.md`.

## 15. Alternatives considered

- **Pull instead of push:** works for Google but needs the customer to hand backd a powerful service account, which is heavier and riskier than a token that can only manage its own scope.
- **SCIM id = a per-organization link id:** keeps backd user ids private and uncorrelated across companies; rejected for the simpler stable id (§3.1).
- **`409` for existing emails in organizations:** the honest SCIM answer, and a cross-tenant account-existence oracle.
- **Token as a secret referenced from `realm.yaml`:** two places to keep in step and a plaintext credential in the secrets store; a generated, hashed token has one.
- **Automatic email linking for provisioned people:** the original objection of [sso.md](./sso.md) holds; only the narrow binding of §3.5 and the verified-domain rule are allowed.
- **Deleting accounts on `DELETE`:** irreversible, wrong for people in several organizations, and a stolen token could erase users.
- **A fixed number of recovery members (2):** replaced by "every manager has a backup", which makes each manager able to recover instead of counting heads.
- **Role names as the SCIM mapping key in `realm.yaml` (`scim_mapping: editor-group`):** group names belong to each company's directory, not to the realm, so organizations map by the provider's group id.
