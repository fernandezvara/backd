# Changelog

All notable changes to `backd` and to its JavaScript client `backd-js`, which are released on the same version from 0.8.2, and to its Dart client `package:backd`, from 0.9.1 (its own changes are also in `clients/dart/CHANGELOG.md`). The upgrade notes, with what needs your action, are in the documentation under [Operations → Upgrading](https://fernandezvara.github.io/backd/docs/operate/); the notes of every release are on the [releases page](https://github.com/fernandezvara/backd/releases).

Until a stable release is declared, a minor release may have breaking changes; they are listed first.

## Unreleased

### Breaking

- **Sizes follow one grammar:** a number and a case-sensitive unit with no space (`512KiB`, `1.5GB`), decimals allowed when the result is a whole number of bytes, in decimal (`KB`...`TB`, powers of 1000) or binary (`KiB`...`TiB`, powers of 1024) units. A function's `memory` takes binary units only (`256MB` is refused: write `256MiB`). The units are explained in [Sizes and units](https://fernandezvara.github.io/backd/docs/build/configuration/#sizes-and-units).
- **`backd` and `backd executor` must run the same version:** the request to the executor carries `memory_bytes` instead of `memory_mb`.

### Added

- **`backd types --lang go`** writes `types.go` (`--package` names the package) for the Go client: a struct per document and per write, string types with constants for enums, constants for the fields of `where` and `order_by`, a `<Realm>Realm` over the client with typed collections (`client.Typed[T]`) and function calls, the app configuration and the role names. `realm.json` and its fingerprint are the same as for the other languages, and `--check` and `--diff` work. The admin types endpoint takes `?lang=go&package=…`.
- **Environment variables with a size** (`MAX_BODY_BYTES`, `BACKD_MAX_UPLOAD_BYTES`, `BACKD_REALTIME_MEMORY`) take a unit as well as a bare number of bytes: `1MiB` and `1048576` are the same value.
- **`backd-js`:** `parseSize(text, { family, allowBytes })` and `formatBytes(bytes, family)` read and print sizes with the server's grammar. The admin interface prints every size with `formatBytes` (`1.5 KiB`, `5 MiB`: no trailing `.0`).
- **Go client (`pkg/client`):** `client.New(Options)` with the request pipeline (`Do`), retries of `429`/`503`, the `*client.Error` types and sentinels (`ErrNotFound`, `ErrConflict`, …), token storage in memory or in a file, per-organization clients and `ParseSize`/`FormatSize`; `Auth()` has sign-up and sign-in (the `SignIn` step machine, second factor, magic link, sign-in with a provider by redirect or identity token), re-authentication, sessions and the account flows; `DB().Collection()` reads and writes documents (lists with cursors and `iter.Seq2` iteration, search, aggregations and `FillBuckets`, `Batch`, `If-Match`, idempotency keys, teams, soft delete) with `Where` operators, the `Expand` builder and `As[T]` for typed documents. The revalidation cache keeps the last body and `ETag` of document and list reads and costs a `304` when nothing changed (on by default, `Cache.Disable` turns it off); `Config()` caches the app configuration per user with `Load`, `Get`, `GetSync`, change events and an optional file copy. Files: `Files(id, field)` (`List`, `Get`, `Put`, `Delete`, `Link`, `Version`), `UploadFile` (through backd, or straight to the storage and in parts when large, with SHA-256 checks and progress), `PrepareUpload`, `FileURL`, `DownloadFile`, `PublicURL` and `VersionStatus`. Functions: `DB().Call`/`Run` and `Functions().Call` with idempotency keys, `WithRespondAsync`, and a `Job` that polls (`Status`, `Wait`, `WaitInto`, steps, `OnProgress`) and fails with the error a synchronous call would have given. Organizations: `Orgs()` (create, update, leave, delete, `SignedIn`, members, teams with role windows, templates, invitations and sign-in connections), `Consents()`, `Account()` (data exports) and `Push()` (devices, `RegisterOnLaunch`). Realtime: `Realtime().Subscribe` and `Collection.Subscribe` keep live views over one multiplexed stream (loaded from normal reads, buffered events, resume tokens, resets with jitter, reconnects with backoff, references, `OnChange`/`Updates`), and `Config().Live` re-reads the configuration when it changes. `Options.MapError` lets a program shape the errors the client returns, and `Error.Path` and `Error.Header` say where a call went and what the server sent back. The `backd` command line is built on the client (and on an internal admin add-on over it), with the same commands, output and errors as before. The guide is [Go client](https://fernandezvara.github.io/backd/docs/build/clients/go/), the example is `clients/go-examples/shelf` (its generated types are checked by `make shelf-types`), and the package documentation has runnable examples. It uses the standard library only.
- **Python client (`clients/python`, package `backd`), under construction:** `Client` and `AsyncClient` over `httpx` (one runtime dependency, Python 3.10 or later, `mypy --strict` clean) with the request pipeline (`request`), retries of `429`/`503`, the `BackdError` hierarchy with the names `backd-js` uses, token storage (`MemoryStorage`, `FileStorage`) and `parse_size`/`format_bytes`. The sync client is generated from the async one. See the [Python client](https://fernandezvara.github.io/backd/docs/build/clients/python/) page.
- **`backd storage usage`** prints sizes with at most two decimals (`1.5 KiB`, `5 MiB`) and stops at `TiB`.

## 0.9.5

### Added

- **Public files (new):** a file field with `public: true` keeps JPEG and PNG pictures in a second, independent `public_storage:` (its own provider, bucket, keys, prefix and the `url` browsers read from; `backd` never connects to it) and puts each file's permanent address in the document (`photo.url`, and `versions.<name>.url` once a version is ready), so a page can show it with no signed link and no request to `backd`. Names are cleaned and must end with the extension of the content (`400 file_extension_mismatch`, never renamed), the metadata is always removed, and an original is cached for a year, a version for a day. Public files are included in personal data exports, realm exports and imports (an import checks them like an upload before publishing them) and left out of anonymized copies. `backd storage check` and `reconcile` take `--storage private|public`; `--direct` takes `--public-storage-key` and `--public-storage-secret`. `backd-js` and `package:backd` have `publicUrl` and `fileUrl(file:)`; the generated types, the admin UI and the workshop example (a public gallery) know them. See [Public files](https://fernandezvara.github.io/backd/docs/build/files/public-files/).
- **`?link=json` on a public file** answers its permanent address with `expires_at: null`; the `expires_at` of `FileLink` is nullable in the Dart client.
- **`POST /_admin/storage/check?storage=public`**, `storage` in the body of `POST /_admin/storage/reconcile`, and `public_storage` in `GET /_admin/storage` and the configuration view.

### Changed

- **The storage is a property of the file:** a file's details say which storage it is in (`public`, `key_name`), and the upload journal and the deletion queue record it. Private behavior is unchanged. The generated types of every realm with files gain `public` and `key_name` (regenerate with `backd types`).

## 0.9.4

### Added

- **Change the password signed out (new):** `POST /_auth/password/update` with `{email, password, new_password}` sets a new password for someone who gives the current one but has no session, for a password that [expired for them alone](https://fernandezvara.github.io/backd/docs/build/auth/users/#expiring-a-password) or one they want to replace. An account with a second factor also sends `code` (a recovery code with `method: "recovery"`). The new password must meet the policy and differ from the current one; wrong proofs are throttled like a sign-in; every session of the user ends and none starts, `password-changed` is sent and the change is audited as `user.password_change`. A password expired for the **whole realm** (`expire-passwords`, the first step after a leak) is refused with `password_expired`, because it may be in the leak. `backd-js` has `auth.updatePassword` and `package:backd` `auth.updatePassword`.
- **A new admin panel:** a top bar with five grouped menus (Identity, Access, Data, Compute, Platform) that opens on click and collapses into one menu on a narrow screen, a breadcrumb that starts at `Realm: <name>` and leads to every part, the account menu with language, theme and sign-out, and pages on one frame (description left, actions right; the visible titles became hidden headings for screen readers). Every page of the old interface is still there, and Jobs and history got its own menu entry.
- **One sign-in form in the admin UI:** email, realm and password in a single step (the realm comes from the address, else from the last sign-in), and when the password expired for the user the form offers to choose a new one with the current one, the new one twice and a code for an account with a second factor.
- **Clearer confirmations in the admin UI:** messages appear under the bar with an icon, an error stays until dismissed, and a test push, an OpenAPI download and a finished schema check now say so.

### Changed

- **A new password clears the user's own expiry:** `password_expired_at` of `GET /_admin/users` goes back to `null` once the user has a new password (set by an administrator, changed, reset or updated signed out), so the list stops marking it as expired. The realm's epoch is not affected.
- **Admin UI:** the leak actions on Users and the schema check of a collection start folded behind a show/hide button; the realm menu and the "choose a realm" page are gone (a session is for one realm: sign out and sign in again); the monospace font stack includes DejaVu Sans Mono and Ubuntu Mono; the title reads `back(d) admin`.
- **Deno 2.9.8:** the executor image and the function bundles are pinned to Deno 2.9.8 (a binary that finds another Deno says so). Go libraries and the admin UI's packages were upgraded.
- **Internal:** shared helpers for the HTTP handlers, the document code and the MongoDB store; no change in behavior.

### Fixed

- **A schema check that finished before its first poll** in the admin UI never loaded its report.

## 0.9.3

### Breaking

- **Every session in a realm with organizations belongs to one organization (34.2):** a person signs in *to* an organization (`/_auth/orgs/{org}/…`) and the session reaches that organization and no other. Documents are created in it and listed from it without saying which; rules see only it (`user.orgs` has one entry, `user.org` is its id, `ctx.user.org` in functions) and the pushdown is `_meta.org == <the organization>`. **Removed:** `?org=` on a session's requests (`400`; the admin data route and functions with `admin: true` still choose with it), `Collection.inOrg()` in the JavaScript and Dart clients and the generated types (`inTeam` needs no `inOrg` before it), `GET /_orgs`, `POST /_orgs/invitations/preview` and `POST /_orgs/invitations/accept` (an invitation is previewed at `/_auth/orgs/{org}/invitations/preview` and taken by signing in with it), `orgs.list()` and `orgs.invitations.preview/accept` in the clients, and `/_auth/signup`, the unscoped magic link request, the realm's own `oauth/{provider}/start`, `id-token` and `/_auth/providers` for the people of the realm (`404`). `POST /_auth/login` is the door of **realm administrators** alone (`401 invalid_credentials` for anyone else); their session belongs to no organization and reaches the admin API. A session from before (without an organization) answers `401 session_unscoped`: the clients treat it as an expired one, and the person signs in again. A member removed from an organization, an organization deleted and a connection removed end the sessions opened in it.
- **The slug is required** (`POST /_orgs`, `POST /_admin/orgs`, `backd orgs create --slug`) and may not look like an id, because it is how people name the organization when they sign in. Organizations made without one get theirs with `backd orgs set-slug` (`PUT /_admin/orgs/{org}/slug`); startup warns about the ones without.
- **Background work keeps its organization:** jobs (`caller_org`) and function callback tokens carry the organization of the session that started them, so a function acting for a user counts only that organization. **Run `backd provision`** (new fields and an index on sessions; with `PROVISION_MODE=verify`, `backd` refuses to start until it has). See [Upgrading](https://fernandezvara.github.io/backd/docs/operate/#upgrading-to-v093).

### Added

- **Security review of scoped sessions (34.7):** a session of an organization that requires its connection can only be made through it (a code, link or challenge issued before, and an attempt with the realm's own provider that began before, are refused); `POST /_auth/orgs` is limited to 20 an hour per address and the sign-in calls to organizations to 120 a minute; `GET /_orgs/{org}/members?sso=false` needs `manage: org`; `GET /_auth/sessions` shows each session's `org` and `connection`.
- **Require the organization's connection (34.6):** `PATCH /_orgs/{org}` with `sso_required: true` (`manage: org`, a fresh proof, a working connection and a session opened through one: `409 sso_not_ready`) makes the connection the only way in. `login`, `signup`, `magic-link`, `reset-password/request` and the realm's own providers answer `400 sso_required` for that organization, `GET /_auth/orgs/{org}/providers` says `sso_required: true` with only the connection's providers, the organization's sessions not opened through a connection end, and the answer counts the members with no identity on the connection (`members_without_sso`, listed by `GET /_orgs/{org}/members?sso=false`). Removing the last working connection turns it off; realm administrators clear it with `PATCH /_admin/orgs/{org}` or `backd orgs sso-required-off`. Audited as `org.sso_required`. The JavaScript and Dart clients gain `ssoRequired` in `auth.options()`, `sso_required` in `orgs.update`, `members.list({ sso: false })` and the `SsoRequiredError` and `SsoSessionError` classes.
- **A connection session can't change the account (34.6):** a session an organization's connection opened (its first method is now `sso:{org}:{provider}`, not the provider's name) answers `403 sso_session` on changing or removing the password, the email, the second factor and its recovery codes, linking or unlinking a provider, deleting the account and the personal data export, before asking for a proof.
- **`session_max_age` per organization (34.2):** `PATCH /_orgs/{org}` shortens the lifetime of the sessions opened in an organization (at least an hour, never more than `sessions.max_lifetime`; a fresh proof is asked), `GET /_auth/me` names the session's organization with `require_mfa` and `mfa_met`, and the JavaScript and Dart `orgs.update` take it.
- **API keys bound to an organization (34.2):** `backd apikey create --org` (`org` in `POST /_admin/apikeys`, `admin.apiKeys.create({ org })`) binds a data key that acts on behalf of users to one organization; without it such a key counts none.
- **The Shelf example signs in to a team (34.5):** the sign-in form asks for the team (its slug, empty for an operator) and offers what it allows (`auth.options`), starting a team takes the operator's invitation (`signUpWithOrg`), "Forgot your team?" emails the address its teams, a team's invitation link (`?join=…&org=…`) shows what it offers and signs the person in with it, the Teams view works in the team of the session and switches between the ones this browser holds (a switch loads the page again in that team), and creating a team opens its session at once. The tour, the Flutter demo and chapter 20 follow, and `organizations.signin_link` is set in the example realm. New guides: [where documents live](https://fernandezvara.github.io/backd/docs/build/organizations/where-documents-live/) and [the sign-in experience](https://fernandezvara.github.io/backd/docs/build/organizations/sign-in-experience/).
- **`POST /_auth/orgs` in an invite-only realm (34.5):** a person holding the realm's invitation (`invitation`, `bdi_…`) starts their company, as anyone does in an open realm; a closed realm still refuses. The JavaScript and Dart `signUpWithOrg` take `invitation`.
- **Scoped sessions in the JavaScript and Dart clients (34.4):** `createClient({ org })` (`BackdClient(org:)`) binds a client to an organization, by id or by the slug people know, and `login`, `signup`, `magicLink.request`, `requestPasswordReset` and `signInWith` go to `/_auth/orgs/{org}/…`; they no longer send an `org` field in the body. `client.org(ref)` gives one client per organization, each with a token of its own, and `client.orgs.signedIn()` lists the ones the app holds; the sign-in answer, `auth.current` and `auth.org()` say which organization a session is scoped to. `auth.options()`, `auth.signUpWithOrg`, `auth.findOrgs` and `auth.previewInvitation` are new (Dart too, which had no organization sign-in), `orgs.create` keeps the session it opens, and a sign-in that returns for an organization (`backd_org`) is kept by that organization's client. **`TokenStorage` gains `slot(name)` and `slots()`** (JavaScript: optional; Dart: breaking for custom storages). `Collection.inOrg()` was removed in 34.2.
- **Signing in to an organization (34.3):** sign-in routes under `/_auth/orgs/{org}/`: `login`, `signup` (by invitation), `magic-link`, `reset-password/request` and `invitations/preview`, which give sessions **scoped to the organization** (`org` in the answer, and in the session) and answer a stranger, an unknown organization and a wrong password alike; `POST /_auth/orgs` lets a new person start a company (account, organization and session in one call); `POST /_auth/orgs/find` emails an address its companies (`organizations-found`, a new email kind; needs `organizations.signin_link`); an invitation is accepted as part of a sign-in (`invitation` in `login`, `signup` and `oauth/start`); an organization's id or slug is accepted by the routes that run before a session, and a slug may no longer look like an id. The unscoped routes still work; nothing is enforced yet (design/scoped-sessions.md). **Run `backd provision`** (the sign-in attempts gain `scope_org`; with `PROVISION_MODE=verify`, `backd` refuses to start until it has).
- **Security review of organization sign-in (30.9):** a Microsoft connection now accepts the address in the token only when it is on the domain of the account's user principal name (`preferred_username`), because a tenant's administrator can write any address in the `email` claim and could otherwise claim someone else's mailbox in the realm (the person who later resets that account's password would keep a sign-in of the attacker's tenant on it); the `email` optional claim must be added to the app registration. `join_roles` follow the granting rules of an invitation: `manage: sso` alone can give none, `manage: members` the roles that open nothing the manager lacks, `manage: roles` any (also when backd re-checks at every join). Imported connections are validated (`<org>:<provider>` id, provider, tenant and domains), and `email_domains` reads the address as the account is made.
- **Organization sign-in in the JavaScript client and the admin UI (30.7):** `backd-js` takes `org` in `auth.signInWith`, `linkProvider`, `signInWithIdToken` and `linkProviderWithIdToken`, `unlinkProvider(provider, { org })` takes the organization, `auth.providers({ org? })` lists the providers to offer, `orgs.sso(id)` offers `list`, `get`, `set` and `delete`, `admin.orgs.sso/setSso/deleteSso` do the same for administrators, and `NotAllowedError` is the typed `not_allowed`. The admin UI's organization page has a Sign-in section: the connections with their redirect addresses, a form with a write-only secret, removal and the recent sign-ins. `GET /_admin/config` shows `organizations.sso`. The Dart client does not have these calls yet.
- **Lifecycle and portability of organization sign-in (30.6):** deleting an organization removes its sign-in connections and every secret kept for it in its cleanup job (counted as `connections` in `org.deleted`; those of an orphaned organization are unavailable); erasing a user already removed all their identities, organization ones included. `org_connections` is one more auth part of `backd export --include auth` and `backd import` (without client secrets: an imported connection is unavailable until its secret is set again), and an anonymized export keeps connections with their client ids blanked.
- **Joining through an organization's connection (30.5):** a person the connection admits for the first time (a new account, or an explicit `intent: link`) joins the organization with the connection's `join_roles`, also in a realm whose `signup` is `closed` or `invite`. A member a manager removed is kept in the connection's `blocked` list and not rejoined until an invitation is accepted (leaving by oneself does not block). The roles are checked at every join: a connection whose last setter lost the capabilities of its `join_roles` is disabled (`org.sso.disabled`). Sessions, login codes and second-step challenges record the organization of the sign-in (`org`; nothing enforces it yet). New audit events `org.sso.login` and `org.sso.disabled`; a join is `org.member_add` with `by: sso`.
- **Organization sign-in (30.4):** `GET|POST /_auth/orgs/{org}/oauth/{provider}/start`, `…/callback` and `…/id-token` sign people in through an organization's connection with the same redirect flow, login code and session as the realm's providers. The verified token must carry the connection's Google Workspace domain (`hd`) or Microsoft tenant (`tid`), a verified address for Google, and an address in `email_domains` when it lists any; otherwise `backd_error=not_allowed` (`403 not_allowed` natively) and nothing is created. It never links an account by address, and an unavailable connection answers like a missing one. `GET /_auth/providers` and `GET /_auth/orgs/{org}/providers` list the providers a client may offer now (public, cacheable for a minute). `DELETE /_auth/identities/{provider}` (and the administrator's) take `?org=`, and identities in `GET /_auth/me` carry their `org`.
- **Organization sign-in connections (30.3):** `organizations.sso` in `realm.yaml` (`enabled`, `providers`, `max_per_org`) and the capability `manage: sso` let the managers of an organization keep its own Google Workspace or Microsoft Entra tenant as a sign-in provider: `GET|PUT|DELETE /_orgs/{org}/sso[/{provider}]` (a change needs a fresh proof; the client secret is write-only and kept as an organization secret) and the realm administrator's `/_admin/orgs/{org}/sso[/{provider}]`, `backd orgs sso|sso-set|sso-delete`. A connection names who may come in (a Workspace domain or a tenant id; `common`, `organizations` and `consumers` are refused) and the roles `join_roles` that follow the granting rules. Off by default and `404` while off. Signing in through a connection arrives with the next steps. **Run `backd provision`** (a new system collection, `org_connections`).
- **Organization-scoped secrets:** the secrets store has a third scope, an organization's, for the client secrets of the sign-in connections organizations will set up themselves (milestone 30, see `design/org-sso.md`). They are sealed with the instance key like every secret, cached per scope, listed with their `org` (never a value) and audited as `secret.set`/`secret.delete` with the organization. Nobody can read one back and `function.yaml` cannot name one, so functions never see them. Realm administrators write and delete them with `PUT|DELETE /_admin/secrets/{name}` and `org` / `?org=`, or `backd secret set|delete --org <id>`; `backd secret rotate-key` re-seals them with the rest. Nothing to provision.

### Changed

- **Documentation:** the tutorial chapters have icons, and Troubleshooting is the last page of the sidebar, after Contribute.
- **One place for the binary in every image:** `backd` is at `/usr/local/bin/backd` in the `backd`, `backd-executor` and production images, with `/backd` a link to it for `docker compose exec backd /backd <command>`. The plain `backd` image's entrypoint is `/usr/local/bin/backd`; an `entrypoint:` or `command:` that names `/backd` keeps working.
- **The worked example of the Organizations section is a knowledge base:** `examples/config/kb` (company pages, team pages that are private, shared with the organization or public, and drafts) replaces the HR absences realm, and the page is `build/organizations/example-knowledge-base/`. The Organizations API page is titled "Organizations API".
- **Organization addresses sign in with the realm's providers too (34.3):** `GET|POST /_auth/orgs/{org}/oauth/{provider}/…` signs in to the organization with the realm's own provider when the organization has no connection of that name, and the person must then be a member (or hold an invitation of the organization, `?invitation=bdo_…`); otherwise the flow ends with `backd_error=not_allowed`. An unknown organization, a deleted one, a disabled connection and a feature switched off now answer like an organization without connections (the realm's providers and `methods`) instead of `404` / an empty list, so nothing says whether an organization exists. `404` is left for a provider that neither the organization nor the realm has, and for a connection without its secret. The organization may now be named by its slug in these routes.
- **`POST /_orgs` also opens a session (34.3):** the answer holds `session: {token, expires_at, org}`, a new session scoped to the organization just made, beside the caller's own.
- **Identities are keyed by organization (30.4):** `identities` gain an optional `org`, and the unique indexes become `(provider, org, subject)` and `(user_id, provider, org)`, replacing `(provider, subject)` and `(user_id, provider)`, so a person can hold the same provider at an organization and at the realm. Nothing is rewritten: **run `backd provision`**, which creates the new indexes and drops the old ones (with `PROVISION_MODE=verify`, `backd` refuses to start until it has).

## 0.9.2

### Breaking

- **A realm keeps its content and configuration in `_realm/`:** `email`, `pages`, `push`, `consents`, `compliance` and `app-config` move from the top of the realm into `<realm>/_realm/` (`app-config` becomes `_realm/config`); `realm.yaml` stays where it is. A realm laid out the old way does not load: the error names each folder and where to move it. Any other folder starting with `_` is now an error (a realm has only `_realm`, a database only `_functions`), and every other folder of a realm is a database, so no name is reserved any more. `backd template` writes the new layout. See [the data model](https://fernandezvara.github.io/backd/docs/build/configuration/config-dir/).

### Added

- **Shelf profiles live at the user's id (tutorial chapter 21):** `profiles` declares `custom_id: user`, so a profile is at `/v1/shelf/main/profiles/<user id>` and there is at most one per person without an index; the `author` reference expands from `_meta.owner` with the default `key: id`, replacing the `key: _meta.owner` recipe, and the unique index on `_meta.owner` is gone. A stack that ran the earlier chapter keeps profiles with generated ids and the old index until you recreate them.
- **Realtime follows role windows to the second:** a stream reads the caller's access again when a role grant's window (`from`/`until` of a team role or an organization role) opens or closes, instead of up to five minutes later, so a subscription that changes gets its `reset` with `access_changed` at the boundary. `_meta.team` is covered by tests as a query field, an `aggregate.group_by` field and a realtime grouping key, as `_meta.org` is.
- **`client.account` (JavaScript and Dart clients):** `requestExport()`, `exports()`, `export(id)`, `waitForExport(id)` and `downloadExport(id)` run the user's [personal data export](https://fernandezvara.github.io/backd/docs/build/clients/js/#your-own-data) from an app: ask (with a fresh proof), follow, and save the zip. The consent calls (`consents.current/text/accept/withdraw`, `signup({ consents })`, the `consentRequired` sign-in result with `acceptConsents`, the typed `ConsentRequiredError`) were already there.
- **Personal data export:** a user can download everything the realm holds about them, and support can produce the same for a formal request. `compliance.export: true` (with `export_page` and `export_retention`, and a realm that has `storage:` and `email:`) turns it on. `POST /_auth/me/export` (a fresh re-authentication, one a day) queues a job that streams a **zip** to the realm's file storage: the documents the erasure model finds for the user (owned, or named in a `pull` field, narrowed by `personal_data`), their files, the system data about their account (no credentials, tokens or other people's details), a manifest with checksums and every exclusion with its reason, and a `README.html` in their language (built-in English and Spanish, or `compliance/readme/<locale>.html`). ### Security

- **Field encryption review:** an `Idempotency-Key` answer is no longer remembered with encrypted fields in plain (they come back `null` with `_meta.redacted` on a replay) and its request hash is keyed; the input of a trigger job leaves out encrypted fields and lists them in `redacted`.
- **Breach response review:** a second step, an enrollment or a consent prompt that a password sign-in started before the passwords were expired can no longer finish into a session; using a reset link uses up the user's other reset links; an anonymized export no longer carries the production history of passwords (`password_expired_at`, `password_notified_at`) and gives the staging password a current change time.
- **Export and import review:** the manifest's authentication parts and every collection part must be the path the format names and be checksummed (a hostile package could make `backd import` read a local file); an imported document's `_meta` is held to the fields the server writes; imported files are held to their field's size; `--auth-key-out` creates a `0600` file even over an existing one; anonymized users lose `admin_networks` and `login_networks`. See the security model page.

### Added

- **Dart client 0.9.1:** `package:backd` joins the release train: it is released on the same version as the server and `backd-js` from here on (it was `0.0.5`), with the same API. See `clients/dart/CHANGELOG.md`.
- **Dart demo moved:** the Flutter Shelf demo is now `clients/dart-examples` (it was `clients/dart/example`, inside the package), so the Dart client builds, tests and publishes with the plain Dart SDK, without Flutter. The Dart workflows use `dart-lang/setup-dart` and the demo keeps its own Flutter job.
- **JavaScript client 0.9.1:** released on the same version as the server. It gains the key, rotation, migration, password and session administration listed below (`admin.secrets.createKey/rotateKey`, `admin.encryption.status/rekey/migrate`, `users.expirePassword`, `users.resetLink`, `passwords.*`, `sessions.revokeAll`), the typed `PasswordExpiredError`, `FieldEncryptedError` and `_meta.redacted`.
- **Documentation: field encryption.** A new [Field encryption](https://fernandezvara.github.io/backd/docs/build/encryption/) section with the concepts (what is and isn't protected, field keys and data keys, why rotation is instant, how it differs from disk and bucket encryption), recipes (a tax id with lookup, notes only doctors read, turning encryption on for a field that has data, moving or turning it off, seeding staging), and every startup, request and command error with what to do; the `fields:` keys in the data model reference; and a field-key section in the *If credentials leak* runbook (a leaked key, leaked data keys, a leaked master key). The key and field guide, the export and import guide and the format specification were written with each part.
- **Shelf tutorial chapter 25, private notes (last part of field encryption):** pins gain `private_notes`, encrypted with a `SHELF_NOTES` key and revealed to the pin's author and the team's admins and owners (`null` and `_meta.redacted` for the rest), with the key created and saved, the ciphertext in MongoDB, an instant rotation and an export that opens the notes only with the key; the tour checks all of it. `backd secret create`, `rotate` and `list` take `--direct`: they work on MongoDB and `CONFIG_DIR` with no running backd and no sign-in, which is how a key is created before the first start of a realm whose configuration names it (backd refuses to start without it) or restored after losing the secrets; `secret create --skip-existing` is for scripts. The example and tutorial stack scripts create `SHELF_NOTES` before starting.
- **Encrypted fields in export and import (sixth part of field encryption):** `backd export` sends encrypted fields as ciphertext (BSON binary subtype 6 in Extended JSON) with `_system/data_keys.jsonl`, the wrapped data and index keys, and lists each field in the manifest with its key's name and fingerprint; the server never decrypts for an export. `--field <path>=<key:|env:|file:…>` (entries separated by `;`) opens fields in the command, checking each key against its fingerprint and naming the field and key when it is wrong; `backd export-decrypt --from <package> --out <dir> --field …` opens fields of a package offline, with no server, database or master key; a direct export needs no master key for them either. `backd import` seals ciphertext again under the target's keys when the target holds the same key (the CLI sends the package's wrapped keys and the target opens the values itself, so a differently named realm works), takes `--field` source keys when it doesn't, builds blind indexes as it writes, refuses (`422`) fields nobody can open and lists them on a dry run. Anonymized copies and CSV extracts keep ciphertext. The storage format is specified, with test vectors that the tests check, in *Operate → Export and import → Encrypted fields format*. Packages made before this have no `database` and `collection` in `encrypted_fields` (there were no encrypted fields).
- **Migrating encrypted data (fifth part of field encryption):** reads accept every form of a value (plaintext from before, older generations and keys, fields no longer encrypted) and writes follow the configuration. `backd encrypt status` / `GET /_admin/encryption` count, per field, plaintext, current and old values and blind index coverage, with keys, fingerprints and generations; `backd encrypt rekey` starts a new data-key generation; `backd encrypt migrate [--dry-run] [--field …]` (`POST /_admin/encryption/migrate`) runs a resumable, rate-limited worker job that encrypts, seals again, builds indexes and opens values of fields no longer encrypted, without changing `_meta.version` or telling triggers and realtime, and retires data keys nothing uses (a retired key no longer blocks deleting its field key). A field moved to another key starts a new generation at startup. `backd` warns at startup about fields not fully migrated. Documents carry two more hidden fields (`_enc`, with the data key id of each encrypted value, and `_bidx`), both reserved; run `backd provision`. `backd-js` gains `admin.encryption.status/rekey/migrate`.
- **Reveal rules for encrypted fields (fourth part of field encryption):** `fields.<path>.reveal` is an access rule (`document`, `user`, `hasRole`, organization helpers) that decides, per document and after the read rule, who sees an encrypted field in plain. A caller it refuses gets `null` and the field in `_meta.redacted`, in reads, lists, batches, write answers, expanded documents (their own collection's rule) and realtime events; writing needs no reveal and a `PATCH` of another field keeps a hidden one. API keys and `ctx.admin.db` see plain values; a full administrator on the admin data route does too, audited as `data.reveal` (fields and count); a read-only administrator never. Answers with hidden fields carry a representation tag in the `ETag` so conditional GET never serves a stale view. `backd-js` types `_meta.redacted` and raises `FieldEncryptedError`; the generated TypeScript types gain `redacted` (run `backd types` again).
- **Search on encrypted fields (third part of field encryption):** `fields.<path>.encrypt` takes `search: equality`, `normalize: [trim, lower, upper]` and `unique: true`. `backd` keeps a hidden, indexed HMAC-SHA-256 of the normalized value under a random index key (wrapped by the field key, rotated with it); `where` with `=`, `$eq` or `$in` on the field is answered through it, `unique` makes two equal values a `409`, and a read rule may compare the field with `==` or `in` against a value that doesn't come from the document (pushed into the query; `!=`, ranges and the rest are refused at startup). Anything else on an encrypted field is still `400 field_encrypted`. Equal values share an index, which the docs warn about for low-variety data. Existing documents have no index until the migration of a later release. A `_bidx` field is reserved. `backd provision` creates the indexes.
- **Encrypted fields (second part of field encryption):** `collection.yaml`'s `fields.<path>.encrypt.key` stores a field encrypted with AES-256-GCM before it reaches MongoDB: any declared field or nested path, any JSON type, bound to its realm, database, collection, path and document id, under a data key per field that the field key wraps. Everything reads the plain value (API, `_batch`, functions, admin data, triggers, realtime); `schema.json` validates the plain value and the database validator expects binary. `backd secret rotate --name HEALTH --generate|--value|--resume` (`POST /_admin/secrets/{name}/rotate`) replaces a key and wraps its data keys again without rewriting a document; the previous value is kept until it is done, and a key with data keys under it can't be deleted. Startup refuses encrypted fields that an index, a reference, a file field, a date, an array, an erase `replace`/`pull`/`unset`, an aggregation or a read rule needs in plain; `where` and `order_by` on an encrypted field answer `400 field_encrypted`. New system collection `data_keys`: run `backd provision`. Collections with encrypted fields can't be exported or imported yet. `backd-js` gains `admin.secrets.rotateKey`.
- **Field keys (first part of field encryption):** `backd secret create --realm r --type key --generate --name HEALTH` (or `--value key:|env:|file:` to import one) creates a 32-byte key that is shown once, with a fingerprint to check a saved copy against; `POST /_admin/secrets` does it through the API, and the listing shows each key's fingerprint and the fields that use it, never its value. Needs full admin access and a fresh proof; audited as `secret.key.create` and `secret.key.delete`; a key a field names can't be deleted, a plain `PUT` can't replace one, and no function or provider can read one. `collection.yaml` accepts `fields.<path>.encrypt.key`, and startup refuses a field whose key is missing or is a plain secret. Encrypting the data follows. `backd-js` gains `admin.secrets.createKey`. A key that is lost is lost for good: save it before using it.
- **Documentation:** [If credentials leak](https://fernandezvara.github.io/backd/docs/operate/if-credentials-leak/), a runbook for a leaked backup, dump or key: the steps in order with their commands, what users will see and measured timings. The backup guide's leak section points to it.
- **Password expiry (first part of breach response):** a password can be expired, so it no longer opens the account until the user resets it. Password identities record `password_changed_at`, the realm has a password epoch (`security_state`), and `backd user expire-password` / `POST /_admin/users/{id}/expire-password` expire one user's. A correct expired password gets `401 password_expired` (a wrong one is still `invalid_credentials`) and queues a reset email; password re-authentication refuses it too. Run `backd provision` to update the system collections' validators. `backd user expire-passwords --realm r --yes` (`POST /_admin/passwords/expire`) moves the realm's epoch to now and ends every session (`--keep-sessions` to keep them); `backd user revoke-sessions --realm r --all --yes` (`DELETE /_admin/sessions`) ends every session alone. Both need full admin access and a fresh proof of identity, and are audited. `--notify` (and `backd user notify-expired`, `POST /_admin/passwords/notify`) starts a resumable job that emails every affected user the new `password-expired` message with a reset link, once each and within the email limits; a refused sign-in sends the same message. `backd user reset-link` (`POST /_admin/users/{id}/reset-link`) prints a one-time reset link for a user the email can't reach, sending nothing, audited as `password.reset_link`. `backd-js` raises a typed `PasswordExpiredError` (`resetEmailQueued` says whether backd queued the email with the link) and its admin client gains `users.expirePassword`, `users.resetLink`, `passwords.state/expireAll/notify` and `sessions.revokeAll`. The admin interface's Users page gets a *Passwords and sessions* panel for a full administrator (expire every password, tell the users, end every session), and a user's page can expire the password and make a reset link. `GET /_admin/passwords` reports the realm's epoch and how many accounts have a password; `GET /_admin/users/{id}` says whether the password is expired now.

- **Documentation:** the guides and reference of [exporting and importing](https://fernandezvara.github.io/backd/docs/operate/administration/export-import/): moving an app, seeding staging, reporting extracts, direct mode, the package format and manifest, every flag, the admin API, the errors with what to do, and keeping packages and keys safe.
- **Export packages:** `backd export --realm r [--db d] [--collection c,…] --out dir [--archive] [--no-files]` writes a realm's documents (soft-deleted ones included, in the API representation with Extended JSON for dates and binary) and files as a lossless package with a checksummed manifest, through `GET /_admin/export` (full admin access, re-authentication for sessions, one export per realm at a time, resumable). Audited as `export` and `export.done`. Import, authentication data, direct mode and anonymized exports follow.
- **Import:** `backd import --from <package|.tar.gz> [--mode create|skip|replace] [--dry-run] [--skip-invalid] [--report file]` verifies the package's checksums, has the running `backd` validate every document against the target realm's configuration (ids, schemas, file limits, unique values, existing documents) before anything is written, uploads the files and writes the documents with their ids and `_meta` kept. Writing is idempotent, so an interrupted import is finished by running it again. Through `POST/PUT/DELETE /_admin/import`; audited as `import` and `import.done`.
- **Anonymized exports for staging:** `backd export --anonymize [--anonymize-config file] [--staging-password env:…] [--anonymize-files keep]` applies each collection's `on_owner_delete` `remove` and `replace` rules to every document (plus per-collection overrides, checked against the schemas), rewrites the emails users are listed under in `pull`/`unset` fields, leaves files out, and with `--include auth` gives users `user-<id>@example.invalid` addresses, drops password hashes (or sets one known password), second factors, devices and external-provider identities. The manifest is marked `anonymized`. New `BACKD_ENV` (`production`, `staging`…): an import warns about a non-anonymized package on `staging` and an anonymized one on `production`. `POST /_admin/export` carries the options that don't belong in a URL.
- **Direct mode:** `backd export --direct` and `backd import --direct` (with `--mongo-uri`, `--master-key`, `--storage-key`/`--storage-secret`, `--force`) run the same export and import in the command, straight on MongoDB and `CONFIG_DIR`, with no server: the master key is needed only for files and the realm-sealed authentication data. Records are audited as `cli:offline` with `offline: true`. A direct import refuses while a `backd serve` instance of the realm is alive (instances now record a heartbeat in `backd___deployment.instances`) unless `--force`. `DELETE /_admin/export` now answers `200` with the export's totals.
- **Authentication data in packages:** `backd export --include auth [--auth-key-out file]` adds the realm's users, identities with password hashes, organizations, memberships, teams, authenticator enrollments and push devices; the fields sealed with the realm's secrets are re-sealed under a one-time export key shown once, and `backd import --auth-key key:|env:|file:` opens them on the operator's machine for the target to seal under its own key. Without the key, users arrive without second factors and devices. Recovery codes can't travel. Audited as `export.auth`.
- **Reporting extracts and CSV:** `backd export --fields a,b.c --where '{…}' --format csv` narrows an export to some fields and the documents matching a filter (for one collection), and writes one RFC 4180 table per collection with flattened columns. Field-selected packages are marked `partial`; CSV is lossy and never importable.

### Added

- **Realtime subscriptions:** `realtime: true` in `collection.yaml` and `POST /v1/{realm}/_realtime`, one server-sent event stream per caller following up to 20 subscriptions (`where` filters or single documents). Chains are bounded (`triggers.max_chain`, `max_chained_per_minute`) and a realm's backlog is capped (`max_backlog`), what can't be queued is recorded as a **gap** — inspectable with `backd triggers status|gaps|resolve` over the admin API and repaired with `backd triggers rescan`. ## 0.8.2

### Breaking

- Lists without `order_by` are ordered by `_meta.created_at`, then `id`. A cursor is opaque; a hand-made `after=<id>` needs `order_by=id`. Every data collection gets a `_meta.created_at,id` index (run `backd provision`).
- A create that sends `id` to a collection without `custom_id` is `400 id_not_allowed` (it was ignored).
- Sensitive account actions ask for a fresh proof (`POST /_auth/reauth`, header `X-Backd-Reauth`); their `password` and `current_password` fields are gone.
- `email.default_locale` and `email.locales` moved to the top level of `realm.yaml` (`default_locale`, `locales`).
- The return parameters of provider sign-in are prefixed `backd_`.
- New system collections: `PROVISION_MODE=verify` instances need `backd provision` first.

### Added

- **Sign-in:** Google, Microsoft and Apple through a redirect or a native ID token, several sign-in methods per user, accounts without a password, magic links and codes by email, a second factor (authenticator app and recovery codes) that a realm can require of roles, `user.mfa` and `user.methods` in rules and functions, a fresh proof for sensitive actions, and the matching commands and admin pages.
- **Push notifications:** device registry, providers (FCM, APNs, browsers), templates, `ctx.push.send`, send records and metrics, development capture and a Push tab in the Mailbox.
- **Compliance:** personal data scope and report, consent documents and records, consents at sign-up and re-acceptance, withdrawal, gating of email and push, and retention at erasure.
- **Caching:** conditional GET for documents and lists, public caching of anonymous reads, and a cache in the JavaScript client.
- **App configuration:** a schema and read rules per realm, versions, history and rollback, conditional reads (`GET /_config`), `appConfig()` in rules and `ctx.config` in functions, and `client.config`.
- **Types and OpenAPI:** `backd types` (TypeScript for the app and for functions, `defineFunction`), `backd openapi` and `GET /_openapi.json` (a document per realm, and an admin one), stale-types detection, and downloads in the admin UI.
- **Development:** `BACKD_DEV=true` reloads the whole config live and rewrites the generated types.
- **Custom ids:** `custom_id` in `collection.yaml` (a pattern, or `user`), creates with `id`, `409 id_taken` with a limit on duplicates, and `backd_id_conflicts_total`.
- **Tutorial:** chapters 16 to 19 (second factor, consents, app configuration, types), and Shelf's `members` keyed by user id.
- **JavaScript client 0.8.2:** the second step and magic links, provider sign-in, push, consents, `client.config`, caching, typed clients, `InvalidIdError` and `IdTakenError`, and the type-level tests are now part of the repository.
